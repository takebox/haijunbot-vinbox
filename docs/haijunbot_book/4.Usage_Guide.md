# 4. Usage Guide

This chapter is HaijunBot's practical operation manual; it describes in detail the usage, parameters, and common scenario examples of the main commands.

Before reading this chapter, we recommend that you first learn about HaijunBot's basic installation and configuration through [Quick Start](./2.Quick_Start.md).

## 4.1 First-Run Configuration

Before you run any `haijunbot` command for the first time, you need to perform a simple configuration to connect to an AI large model platform.

### Quick Configuration (Recommended)

We provide an interactive configuration command `hqc` (haijunbot-quick-config), which guides you through configuration quickly:

```bash
# Run the interactive configuration wizard
hqc
```

This command guides you to:

1. Choose an AI platform (OpenAI or Haijun)
2. Enter the API base URL and API key
3. Choose an available model
4. Configure the Normal/Smart/Cheap models
5. Test API connectivity
6. Automatically save the configuration to `~/.haijunbot/config.yaml`

### Generating the Configuration File

When you run any haijunbot command for the first time (for example `haijunbot` or `hpm info`), the system automatically creates a `~/.haijunbot/` folder in your user home directory, along with a default configuration file `config.yaml`.

### Editing the Configuration File

Open the `~/.haijunbot/config.yaml` file. You will see a structure similar to the following:

**The new configuration approach (llm_groups and llms) is recommended**:

```yaml
# yaml-language-server: $schema=https://raw.githubusercontent.com/takebox/HaijunBot/main/docs/schema/config.schema.json

# ====== Basic configuration ======
# Set the model group used by default
llm_group: default

# Multi-line input submit shortcut configuration (optional)
# Supports array format or string format (comma-separated)
# Default values are Ctrl+J and Ctrl+]
# Common shortcuts: c-j (Ctrl+J), c-] (Ctrl+]), c-enter (Ctrl+Enter)
submit_keys:
  - c-j
  - c-]

# ====== Model group configuration ======
# You can define multiple model groups and switch via llm_group
llm_groups:
  default: # Default model group
    normal_llm: gpt-5 # References a model defined in llms below
    # Optionally configure a cheap model and a smart model
    # cheap_llm: gpt-3.5-turbo
    # smart_llm: gpt-5

# ====== Model definitions ======
llms:
  gpt-5:
    platform: openai # Platform type
    model: gpt-5 # Model name
    max_input_token_count: 128000 # Model maximum input token count

    # Model-specific configuration (llm_config)
    llm_config:
      openai_api_key: "your-api-key-here" # Replace with your API key
      openai_api_base: "https://api.openai.com/v1" # API base address, can be used for a proxy
      openai_extra_headers: '{"X-Source": "haijunbot"}' # Additional HTTP headers (optional)

# ====== Environment variable configuration ======
# Legacy configuration approach (still supported, but the llm_config above is recommended)
ENV:
  # OpenAI
  OPENAI_API_KEY: ""
  OPENAI_API_BASE: ""
```

**Legacy configuration approach (still supported)**:

```yaml
# yaml-language-server: $schema=...
# ... other configuration ...
ENV:
  # OpenAI
  OPENAI_API_KEY: ""
  OPENAI_API_BASE: ""

  # Haijun
  JUGLOW_API_KEY: ""
  JUGLOW_API_BASE: ""
```

### Filling in Credentials

**Using the new configuration approach (recommended)**:

1. Define your models in the `llms` section, and fill in the corresponding credentials in `llm_config`.

**Using the legacy configuration approach**:

Simply fill in your API Key or other credential information in the `ENV` section.

> **Note**: New versions recommend the `llm_groups` and `llms` configuration approach, which provides more flexible model management. The `ENV` configuration approach is still supported, but migrating to the new approach is recommended.

**API Key Polling Support**:

API Key now supports configuring multiple Keys, which are automatically polled during requests. This is suitable for scenarios that need to spread request pressure or avoid rate limiting on a single Key. The following formats are supported:

- **Single Key (string)**: `openai_api_key: "sk-xxx"` — Same behavior as before
- **Comma-separated (string)**: `openai_api_key: "sk-xxx1,sk-xxx2,sk-xxx3"` — Automatically split and polled
- **List format**: `openai_api_key: ["sk-xxx1", "sk-xxx2", "sk-xxx3"]` — Used directly and polled

Environment variables also support the comma-separated format: `OPENAI_API_KEY=sk-xxx1,sk-xxx2,sk-xxx3`

After saving the file, HaijunBot is configured and ready to use.

## 4.2 Automatic Prompt Optimization

HaijunBot provides an automatic system prompt optimization feature that, based on your specific task requirements, automatically optimizes the Agent's system prompt to better fit the task scenario and improve task execution efficiency.

### Feature Description

When you use the `-o` or `--optimize-system-prompt` parameter, the system does the following on the first run:

1. **Analyze user requirements**: Use the LLM to analyze your task description and understand the task intent and scenario
2. **Optimize the system prompt**: While keeping the original core functionality and architecture unchanged, enhance or adjust the descriptions of relevant parts in a targeted way
3. **Apply the optimization result**: Apply the optimized prompt to the Agent so that it better understands and executes your task

### Usage Scenarios

- **Domain-specific tasks**: When a task involves a specific domain (such as code development, data analysis, security auditing, etc.), the optimized prompt emphasizes the relevant best practices
- **Customization for complex tasks**: For complex multi-stage tasks, the optimized prompt can better guide the Agent's execution strategy
- **Task scenario adaptation**: Automatically adjust the focus of the prompt according to different task scenarios (such as code generation, code review, problem diagnosis, etc.)

### Usage Examples

```bash
# Enable prompt optimization for the general agent
hjb -o -T "Analyze the issue of Kubernetes Pod startup failure and provide a solution"

# Enable prompt optimization for the code agent
hca -o -T "Implement a complete microservices architecture, including service registration, a configuration center, and an API gateway"

# Combine multiple parameters
hca -o --worktree -T "Refactor the entire user management module, using the new design pattern"
```

### Notes

- Prompt optimization is performed only once on the first run to avoid repeated optimization
- The optimization process consumes extra LLM calls, but usually significantly improves task execution quality
- If optimization fails, the system automatically falls back to the original system prompt, without affecting task execution
- The optimized prompt keeps the original core functionality unchanged, ensuring backward compatibility

## 4.3 General Interaction Tips

No matter which HaijunBot tool you use, mastering the following interaction tips will greatly improve your efficiency.

### 1. Shortcuts (Multi-line Input Mode)

When you need to enter multi-line text (such as in the interactive modes of `hjb` or `hca`), you can use the following shortcuts:

| Shortcut   | Function                                                                                    |
| ---------- | ------------------------------------------------------------------------------------------- |
| `@`        | Triggers file/instruction completion for "Git file mode"; if fzf is installed, a Git file selector pops up. |
| `#`        | Triggers file completion for "full file mode" (excluding .git); if fzf is installed, a full file selector pops up. |
| `Tab`      | Select an item in the pop-up completion suggestion list.                                    |
| `Enter`    | Applies the selected item when the completion list is open; otherwise inserts a newline.    |
| `Ctrl + J` | Submit your multi-line input to start executing the task.                                   |
| `Ctrl + ]` | Can also be used to submit your multi-line input.                                           |
| `Ctrl + C` | Cancel the current input operation.                                                         |
| `Ctrl + O` | Copy the AI's previous reply to the system clipboard for your convenience.                  |

### 2. Prompting Tips

Writing high-quality prompts is the key to unleashing HaijunBot's full potential.

- Clarify the role and goal: At the start of a task, clearly tell HaijunBot what role it should play and what the final goal to achieve is.
  > Example: "You are now a senior operations expert. My goal is to troubleshoot and resolve a Kubernetes Pod startup failure."
- Provide context and special instructions (`@`/`#`): Using the `@` or `#` symbols triggers powerful context completion and quick instruction features.
  - Provide file context: Typing `@` or `#` followed by a file name (supports fuzzy search and auto-completion) injects the file content into the conversation, giving the AI sufficient analysis background.
    - `@` Git file mode: Completion/selection only among files tracked by Git; the list is clean and faster.
    - `#` full file mode: Completion/selection across the entire working directory, automatically excluding `.git`, suitable for files not under Git.
    - If fzf is installed on the system, pressing `@`/`#` pops up the corresponding file selector; otherwise the built-in completion list is used.
    - After selection, the path is inserted wrapped in single quotes; if there is a fragment before the cursor that starts with that prefix and contains no spaces, it is replaced entirely with the selected path.
      > Example: "Please analyze the code in the file `@./src/main.py` and find potential performance bottlenecks."
      > Example: "Please analyze the content of the file `#./logs/latest.log` and locate the source of the error stack."
  - Execute special instructions: After typing `@` or `#`, the completion menu also shows a series of built-in instructions for quickly controlling the conversation or performing common operations.

    > Example: Type `'<Summary>'` and submit to ask HaijunBot to summarize the previous conversation.

    The following are all the available built-in special instructions:

    | Instruction          | Function Description                                                                                                                                                                             |
    | -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
    | `'<Summary>'`        | Ask the AI to summarize the current conversation history and use the summary as new context; this helps maintain focus in long conversations.                                                   |
    | `'<Clear>'`          | Clear the current conversation history and start a brand-new conversation.                                                                                                                       |
    | `'<ToolUsage>'`      | Show the list and detailed descriptions of all available tools, helping you understand what the AI can do.                                                                                       |
    | `'<ReloadConfig>'`   | Reload HaijunBot's configuration file. If you modified the configuration at runtime, you can use this instruction to make it take effect.                                                          |
    | `'<SaveSession>'`    | Save the current conversation state (including history). The session file is named with a timestamp (format: saved_session_YYYYMMDD_HHMMSS.json). It can later be restored via `hjb --restore-session`. **Note**: This instruction is only available in the hjb/hca main program. |
    | `'<RestoreSession>'` | Restore a previously saved session. The system automatically finds the latest session file (sorted by timestamp). **Note**: This instruction is only available in the hjb/hca main program.       |
    | `'<ListSessions>'`   | List all saved session files, including file name, timestamp, and size, helping you quickly find the session to restore.                                                                         |
    | `'<Pin>'`            | Pin content to subsequent conversations. Content after `'<Pin>'` will be pinned and automatically appended to the beginning of every subsequent user input; suitable for context information that needs repeated reminders. |
    | `'<Quiet>'`          | Switch to non-interactive mode (unattended mode). In this mode, all operations that require confirmation automatically continue, without pausing to wait for user input.                          |
    | `'<rule:rule_name>'`    | Dynamically load the specified rule. Rules are searched from the project rules directory (`.haijunbot/rules/`), the rules file (`.haijunbot/rules.yaml`), or the central rules repository, and injected into the conversation. |
    | `'<custom_tag>'`     | You can define your own tags via `replace_map` in `~/.haijunbot/config.yaml`, used to insert preset template text. This is very useful for repetitive input.                                        |

- Break down complex tasks: For complex tasks, break them into smaller, more specific steps and guide HaijunBot to complete them step by step.

### 3. Human-in-the-Loop

One of HaijunBot's core features is the ability to support human intervention at any stage of task execution.

- Pre-execution confirmation: Before executing operations that may have an impact (such as running scripts or modifying files), HaijunBot pauses and requests your confirmation `[Y/n]`. This is the first layer of protection.

- Post-thinking intervention (`Ctrl+C`): This is the most critical intervention method.
  - When the AI is "thinking" (that is, the large model is generating the next step plan), you can press `Ctrl+C` at any time.
  - HaijunBot will not immediately interrupt the model's thinking, but will wait for the current thinking step to finish (that is, the API returns a result).
  - Before executing the plan generated by the model (such as calling a tool), the system detects the interrupt signal, pauses execution, and prompts you: "Interrupted during model interaction, please enter user intervention information:".
  - This gives you a valuable opportunity to review and veto the AI's next action. You can enter a new instruction to correct it, or directly reject the tool call it is about to execute.

- Tool call adjudication: This is a concrete manifestation of "post-thinking intervention". When you interrupt an imminent tool call, the system asks you whether to continue processing that tool. This gives you the final say over each specific operation.

- Force quit (multiple `Ctrl+C`): If you want to terminate the entire HaijunBot program immediately without waiting for the current thinking step to finish, you can quickly press `Ctrl+C` five or more times in succession (or press and hold). This triggers the system's force-quit mechanism.

### 4. Non-interactive Mode (Automation)

For scenarios that need to run HaijunBot in an automated environment (such as CI/CD pipelines or scheduled task scripts), you can use the `-n` or `--non-interactive` parameter to enable non-interactive mode.

This mode has the following characteristics:

- No user prompts: In this mode, HaijunBot will not ask any questions that require the user to enter a `[Y/n]` confirmation or make a selection. All interactive steps are skipped.
- Mandatory task input: Since the task cannot be entered interactively at runtime, the initial task must be provided in the startup command via parameters (such as `hjb -T "..."`, `hca -T "..."`). If not provided, the program exits with an error.
- Disabled interactive features: Some purely interactive features are automatically disabled, such as the feature where `hjb` detects a Git repository at startup and asks whether to switch to `hca`.
- Script execution timeout: To prevent automation scripts from hanging unexpectedly, in non-interactive mode, scripts executed by the `execute_script` tool have a default timeout limit of 5 minutes.

This parameter is key to achieving HaijunBot automation and is suitable for all scenarios that require unattended execution.

## 4.4 General-Purpose Agent (`haijunbot` / `hjb`)

`hjb` is your general-purpose AI assistant, suitable for a variety of open-ended, non-specific tasks.

### Core Capabilities

- Task analysis and planning: Understand complex goals and break them down into execution steps.
- Multi-tool collaboration: Intelligently select and combine tools such as file reading/writing, code execution, and web search.
- System interaction: Able to execute Shell commands to interact with your operating system.
- Predefined tasks: Supports loading preset tasks from the configuration file, simplifying repetitive work.

````bash
## 4.5 Code Agent (`haijunbot-code-agent` / `hca`)

`hca` is an agent designed specifically for software development tasks, and is your capable assistant for daily coding, refactoring, and debugging.

### Core Capabilities

- **Deep code integration**: Automatically analyzes the codebase structure, dependencies, and recent commit history to provide comprehensive context for the task.
- **Smart context recommendation**: Automatically recommends relevant code context at task startup, improving code comprehension efficiency.
- **Automated Git workflow**:
  - **Automatic checkpoint (preprocessing)**: Before entering a task, if uncommitted changes are detected, a standardized commit is made via GitCommitTool (customization via --prefix/--suffix is supported), or, depending on configuration, it only warns and continues.
  - **Incremental changes (interactive patch)**: After each step of the AI's operation (such as modifying a file), a patch containing a `diff` is generated, and you are guided to confirm whether to commit it.
  - **Post-task review (final merge)**: After the entire task is completed, the commits within this session are listed; you can choose "accept" (the system first resets back to the task's starting point, and then GitCommitTool generates a unified and standardized final commit) or directly reset back to the state before the task started.
- **Automated build verification**: Automatically detects the build system (Rust/Cargo, Python, Node.js, Java/Maven/Gradle, Go, CMake/Makefile, etc.) and verifies the build, ensuring the code compiles.
- **Static code analysis**: After generating code modifications, it automatically runs static checks (ruff, mypy, clippy, eslint, etc.) to ensure code quality.
- **Impact scope analysis**: Automatically analyzes the impact scope of code modifications, including dependency chains and interface changes, and assesses the risk level.
- **Code review and verification**: Performs code review and task completion verification through independent ReviewAgent and VerificationAgent, addressing the hallucination problem of large models.
- **Task list management**: Supports modular execution of complex tasks, automatically creating subtasks, managing dependencies, and tracking task status.
- **Virtual terminal support**: CodeAgent supports a virtual terminal tool, allowing interactive operations and expanding the capability boundary of the code agent.
- **Rule system**: Supports loading project rules and named rules to guide code generation and modification behavior.

### Common Parameters

| Parameter                        | Description                                                                                                                              |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `-T`, `--task`                   | The task description to process (the task content can be provided directly on the command line).                                          |
| `--task-file`                    | Read the task description from a file (supports plain text or JSON format).                                                               |
| `-g`, `--llm-group`              | Temporarily specify the model group, overriding the default configuration.                                                                |
| `-G`, `--tool-group`             | Temporarily specify the tool group, overriding the default configuration.                                                                 |
| `-f`, `--config`                 | Specify the path to a custom configuration file.                                                                                          |
| `--append-tools`                 | The list of additional tools, with multiple tools separated by commas, e.g.: `read_webpage,file_analyzer`.                                |
| `-r`, `--restore`                | Interactively select a session to restore.                                                                                                |
| `-R`, `--restore-session`        | Restore from the specified session file.                                                                                                  |
| `--prefix <text>`                | Add a prefix to the subject of the generated commit message (separated by a space).                                                       |

### Examples

1. Add a new feature
   Add a new feature to the project; `hca` automatically finds the relevant files and modifies them.

```bash
hca -T "In the user authentication module, add a 'forgot password' feature. A new API endpoint /api/forgot-password needs to be created, and the logic for sending reset emails implemented."
```

1. Fix a Bug
   Fix the problem according to the Bug description.

```bash
hca -T "Fix the division-by-zero error in src/utils/calculator.py. When the divisor is zero, it should return an error message instead of throwing an exception."
```

1. Code refactoring
   Optimize existing code.

```bash
hca -T "Refactor the src/services/user_service.py file, splitting the overly long 'create_user' method into several smaller private methods to improve code readability."
```

   Load specific rules to guide code generation behavior.

```bash

hca --rule-names tdd,clean_code -T "Implement user login functionality"

hca --rule-names project_style -T "Add a new API endpoint"

   If automatic code review is not needed, you can disable it to speed up execution.

   Control the maximum number of code review iterations to avoid infinite loops.

```bash

1. Append additional tools
   Add additional tools to CodeAgent to extend its functionality.

```bash

```

1. Use automatic system prompt optimization
   For complex code tasks, you can use the `-o` parameter to enable automatic system prompt optimization, so CodeAgent better understands the task scenario and coding conventions.

# Enable prompt optimization for a new feature development task

1. Non-interactive mode (CI/CD)
   Use non-interactive mode in an automated environment.

### Project Rules (.haijunbot/rules and rules.yaml)

To unify AI modification behavior within a team or project, hca supports two ways to define rules: a plain text rules file and a YAML-format named rules file.

#### Plain Text Rules File (.haijunbot/rules)

- What are project rules
  - A plain text file located in the project root directory: `./.haijunbot/rules`
  - Used to constrain and guide the specific behavior of CodeAgent (such as modification scope, style conventions, tool usage strategy, etc.)

- How it takes effect
  - After hca starts, it first reads the "global rules": `~/.haijunbot/rules` in the data directory (or `data_path/rules`), as well as the "project rules": `.haijunbot/rules` of the current repository
  - The system concatenates and merges the contents of the two in the order of "global first, project second"
  - The merged result is injected into the system prompt as a single `<rules>...</rules>` block; project rules are used to override or supplement global rules, and it is recommended to clearly override entries in the project rules
  - After injection, it affects all operations and decisions "within this session"

- Scope of application
  - Global rules: apply to all projects (stored in the data directory `~/.haijunbot/rules` or `data_path/rules`)
  - Project rules: apply only to the current project repository (its git root directory); used to override or supplement global rules

- Recommended style
  - Concise, clear, and executable; prefer an itemized rule list
  - Focus on conventions relevant to the current project, avoiding lengthy background descriptions
  - Stay consistent with the team's existing conventions (code style, commit conventions, directory conventions)

- Example rules file (`.haijunbot/rules`)

  ```
  # Modification scope and constraints
  - Only files within the src/ and docs/ directories may be modified
  - Creating/deleting database tables and migrations is prohibited: migrations/ and database/schema.sql must not be edited
  - All changes to sensitive files such as .env, secrets/*, certificates/keys are rejected

  # Style and quality
  - Python uniformly uses Black and isort; naming follows PEP 8
  - New functions must provide a docstring and necessary type annotations
  - Complex changes provide a minimal reproducible example and necessary unit tests

  # Tools and process
  - File editing prefers PATCH; use REWRITE only when a whole-file rewrite is needed
  - Before any modification, first use read_code to read the target file and context
  - After generating a patch, run static checks (such as flake8/mypy/ruff, etc.) in one go first

  # Git commit
  - Use the Angular commit convention, and a scope must be included
  - --prefix/--suffix may be used to uniformly inject task IDs and signatures
  ```

- Usage steps
  1. Create the directory and file in the project root directory: `mkdir -p .haijunbot && touch .haijunbot/rules`
  2. Write the above rules or the team's custom rules into `.haijunbot/rules`
  3. Commit them to the repository for team sharing and review
  4. Run `hca ...` and the rules take effect automatically; if you modified the rules, re-run `hca` to apply the latest content

- Notes
  - An empty file does not take effect; read failures are safely ignored (they do not block the task)
  - Takes effect only at the local project level and does not affect the global level; global preferences can be saved using the "memory system"
  - Paths and case must match the actual project; for Windows/Linux path differences, write them as they actually are
  - Rules should avoid conflicting with the project's existing toolchain (such as pre-commit, formatters, CI conventions)

#### Named Rules File (rules.yaml and .haijunbot/rules/ directory)

Besides the plain text rules file, hca also supports managing multiple reusable rule sets through a YAML-format named rules file and independent rule files.

**Rule sources and priority**:

Named rules can be loaded from multiple sources, following a strict priority order:

1. **Central rules repository** (highest priority): a configurable Git repository, supporting automatic cloning and daily updates
2. **Project `rules/` directory**: independent rule files under the project root `.haijunbot/rules/` directory
3. **Project `rules.yaml`**: the project root `.haijunbot/rules.yaml` file
4. **Configured rules directory**: additional rule loading directories specified by the user in the configuration file
5. **Global `rules.yaml`**: the `rules.yaml` file in the global data directory
6. **Global rules directory**: the `rules/` directory in the global data directory
7. **Built-in rules** (lowest priority): rules built into the HaijunBot system

**Rule file format**:

- **YAML format** (`rules.yaml`): key-value format, where each key represents a rule name and its value is the rule content
- **Independent files** (`.haijunbot/rules/` directory): one file per rule; the file name (without extension) is the rule name

**How it takes effect**:

- When using the `--rule-names <name_list>` parameter, hca searches for the specified rules from all the above sources
- The system searches for rules in priority order and stops once found (higher priority overrides lower priority)
- All found rule contents are merged and injected into the system prompt together with the plain text rules (`.haijunbot/rules`)
- The rule content is wrapped with the `<rules>...</rules>` tag and injected into CodeAgent's system prompt

**Example rule files**:

**Global rules file** (`~/.haijunbot/rules.yaml`):

```yaml
python_best_practices: |
  - Python code must follow the PEP 8 convention
  - All functions must include type annotations and docstrings
  - Use Black for code formatting
  - Use isort for import sorting

security_guidelines: |
  - The use of eval() and exec() is prohibited
  - All user input must be validated and escaped
  - Sensitive information must not be hardcoded in the code
```

**Project rules file** (`./.haijunbot/rules.yaml`, overrides global rules with the same name):

```yaml
python_best_practices: |
  - Python code must follow the PEP 8 convention
  - All functions must include type annotations and docstrings
  - Use Black for code formatting
  - Use isort for import sorting
  - Additional requirement for this project: all asynchronous functions must use asyncio.create_task() to manage tasks
```

**Project independent rules file** (`./.haijunbot/rules/tdd.md`):

```markdown
# TDD Rules

- All new features must have tests written first
- Tests must cover the main functional paths and edge cases
- The use of the todo!() macro is prohibited
- Test code and implementation code must be separated
```

**Usage steps**:

1. Create the rules file (optional):
   - Global rules: `touch ~/.haijunbot/rules.yaml`
   - Project rules: create `.haijunbot/rules.yaml` or the `.haijunbot/rules/` directory in the git root directory
2. Define rules in the file, in the format of key-value pairs (YAML) or independent files (directory)
3. Run `hca --rule-names <rule_name_list> -T "<task_description>"` to use the specified rules

```bash
# Use multiple rules (comma-separated)
hca --rule-names tdd,clean_code -T "Implement user login functionality"

# Use project-specific rules
hca --rule-names project_style -T "Add a new API endpoint"

# Rules are automatically searched from all sources and loaded by priority
```

**Dynamic rule injection**:

Besides loading rules via the `--rule-names` parameter, you can also dynamically inject specific rules in user input using the `'<rule:rule_name>'` marker:

```bash
# Use in interactive input
hca
# Then type: '<rule:tdd>' implement user login functionality
```

`builtin_input_handler` intercepts this marker, finds the corresponding rule content, replaces it with the format wrapped in the `<rule>...</rule>` tag, and inserts it directly into the user input.

### Rule Placeholders (Jinja2 Templates)

Rule files support Jinja2 template syntax, and can dynamically insert the following built-in variables:

- `{{ current_dir }}`: the current working directory
- `{{ script_dir }}`: the directory where the script is located
- `{{ haijunbot_data_dir }}`: the haijunbot data directory
- `{{ haijunbot_src_dir }}`: the haijunbot source code directory
- `{{ git_root_dir }}`: the git root directory
- `{{ rule_file_dir }}`: the directory where the current rule file is located

**Example**:

```yaml
project_paths: |
  - Only files within the {{ current_dir }}/src/ directory may be modified
  - The configuration file is located at {{ rule_file_dir }}/config/
  - Project root directory: {{ git_root_dir }}
```

If rendering fails (such as a syntax error), the system automatically returns the original content, ensuring backward compatibility.

**Notes**:

- Rule names are case-sensitive and must exactly match the key in the file or the file name
- If the specified rule name does not exist, it is safely ignored (it does not block the task)
- Rules from a higher-priority source override rules with the same name from a lower-priority source
- Rule values can be multi-line strings (using YAML's `|` or `>` syntax)
- Named rules and plain text rules (`.haijunbot/rules`) can be used at the same time, and they are merged together
- The central rules repository requires the `central_rules_repo` configuration item to be configured in the configuration file first

## 4.7 Git Commit Assistant (`haijunbot-git-commit` / `hgc`)

`hgc` can automatically analyze your code changes and generate Git commit messages that conform to conventions.

### Core Capabilities

- Automatically analyze `git diff`: `hgc` automatically stages (`git add .`) all changes in your working tree and analyzes their `diff` content.
- Intelligently handle large changes: If the code changes are very large, `hgc` automatically saves the `diff` as a temporary file and uploads it, instead of injecting it directly into the prompt, avoiding exceeding the model's context limit.
- Generate convention-compliant commit messages: Based on the code changes, the AI generates a commit message that conforms to the conventional commit convention.
- Fully customizable: You can customize all of `hgc`'s behavior through the configuration file, including the commit message template and the prefix/suffix.

### Common Parameters

| Parameter               | Description                                            |
| ----------------------- | ------------------------------------------------------ |
| `--prefix <text>`       | Add a fixed prefix before the subject of the generated commit message. |
| `--suffix <text>`       | Add a fixed suffix to the end of the generated commit message (appended after a newline). |
| `--root-dir <path>`     | Specify the root directory of the Git repository to operate on (defaults to the current directory). |
| `-g/--llm-group <group_name>` | The model group to use, overriding the setting in the configuration file. |

### Examples and Customization

1. Basic usage
   After you have made some code modifications, simply run the following in the project root directory:

```bash
# hgc automatically stages all changes; no manual git add is needed
hgc
```

HaijunBot will analyze the changes, generate a commit message like `feat(auth): add password reset endpoint`, and automatically execute `git commit`.

1. Add a prefix and suffix
   If you want to include a task ID or a specific marker in the commit message, you can use `--prefix` and `--suffix`:

```bash
hgc --prefix "JIRA-123:" --suffix "Reviewed-by: @YourName"
```

The generated commit message will look like:

```
JIRA-123: feat(auth): add password reset endpoint

Reviewed-by: @YourName
```

1. Customize the commit template (advanced)
   One of `hgc`'s most powerful features is that it allows you to completely rewrite the prompt template used to generate the commit message. You can define your own template by setting the `git_commit_prompt` configuration item in the `~/.haijunbot/config.yaml` file.

First, open the configuration file via `hjb -e`, then add the `git_commit_prompt` configuration item:

```yaml
# ~/.haijunbot/config.yaml

# ... other configuration ...

git_commit_prompt: |
  Generate a Chinese commit message that conforms to the [Angular commit convention] for the following code changes.

  # Rules
  1. Must include type, scope, and subject.
  2. The type can only be: 'new feature', 'fix', 'docs', 'format', 'refactor', 'test', 'build', 'continuous integration'.
  3. The scope must be the name of the modified module in the code.
  4. The detailed description part must explain the reason for the change and the benefits it brings.

  # Changes
  {diff}
```

By customizing this template, you can make `hgc` fully follow your team's specific commit convention.

### Tool Configuration Groups

HaijunBot supports defining and switching between different tool combinations through `tool_groups` and `tool_group`. This is very useful for different types of tasks (for example, code development vs. document processing vs. system management), allowing you to quickly switch the available toolset through configuration.

Example: defining and using tool groups

```yaml
# ~/.haijunbot/config.yaml

# 1. Define different tool configuration groups
tool_groups:
  - coding: # Code development group
      use: # Only use these tools
        - execute_script
        - read_code
        - clear_memory
        - save_memory
        - retrieve_memory
  - document: # Document processing group
      use:
        - save_memory
        - retrieve_memory
  - system: # System management group
      dont_use: # Exclude these tools
  - restricted: # Restricted group
      use:
        - read_code
      # Only read_code is allowed, suitable for read-only scenarios

# 2. Choose the tool group to use
tool_group: coding

# Note:
# - If a use list is configured, only the tools in the list are available
# - If a dont_use list is configured, the tools in the list are excluded
# - If both use and dont_use are configured, use takes precedence
# - By default (no tool group set), all tools are available
```

Through tool configuration groups, you can:

- Improve security: limit the available tools in certain scenarios to avoid misoperations
- Optimize experience: provide a streamlined toolset for a specific task type
- Switch quickly: quickly switch work modes by modifying `tool_group`

## 4.8 Smart Shell (`haijunbot-smart-shell` / `hss`)

`hss` is a powerful tool that converts your natural language instructions into executable Shell commands, greatly lowering the barrier to performing complex operations in the terminal.

### Subcommands

- `request [requirement]`: Convert a natural language requirement into a Shell command. If no requirement is provided, it enters interactive input mode.
- `install [--shell <type>]`: Install the "command not found" handler for the specified shell (supports `fish`, `bash`, `zsh`; default `fish`).
- `uninstall [--shell <type>]`: Uninstall the handler for the specified shell (supports `fish`, `bash`, `zsh`; default `fish`).

### Examples

1. Convert a command directly
   When you are unsure of the command for an operation, you can ask `hss` directly. It prints the corresponding Shell command but does not execute it.

```bash
hss request "Find all .log files larger than 1MB in the current directory"
# Output: find . -type f -name "*.log" -size +1M
```

1. Interactive command execution
   If you run `hss request` directly without any arguments, it starts an interactive input interface. In this mode, after you enter a requirement, the generated command is executed immediately.

```bash
# Start interactive mode
hss request

# At the prompt, type: Find all .log files larger than 1MB in the current directory, then press Ctrl+J
# hss will print and execute the find command
```

1. Install the "command not found" handler (supports Fish / Bash / Zsh)
   This is one of `hss`'s powerful features; it lets you operate the terminal as if using natural language.

```bash
# 1. Install the handler (default fish; --shell can specify bash/zsh)
hss install

# 2. Make the configuration take effect (only needs to be done once)
source ~/.config/fish/config.fish
```

After installation, when you type a command in the `fish` terminal that the system does not recognize (and whose length is greater than 10 characters, to prevent accidental triggers), `hss` automatically intercepts this input, converts it into a valid Shell command, and executes it.

```fish
# In a fish shell with the handler installed, type directly:
> Create a folder named 'backup' in the current directory

# hss will automatically convert it and execute: mkdir backup
```

1. Uninstall the handler

```bash
# 1. Uninstall the handler
hss uninstall

# 2. Make the configuration take effect
source ~/.config/fish/config.fish
```

## 4.10 Advanced Git Tools

Besides `hgc`, HaijunBot also provides a series of advanced Git tools to simplify complex operations.

### Interactive Squash (`haijunbot-git-squash` / `hgs`)

`hgs` can help you automatically squash all commits after a specified commit into a brand-new, independent commit, and generate a clear, summary commit message for it. This is very useful when merging multiple small feature commits or fix commits.

#### How It Works

1. Confirm operation: `hgs` first asks you to confirm the squash operation.
2. Reset: It executes `git reset --mixed <the base commit you specify>`. This operation moves the `HEAD` pointer back to the commit you specify, while keeping all the code changes during that period in your working tree.
3. Recommit: Finally, `hgs` calls `hgc` (the Git commit assistant) to make all changes in the working tree a brand-new commit, with the AI analyzing these changes to generate a high-quality summary commit message.

#### Parameters

| Parameter     | Description                                                          |
| ------------- | -------------------------------------------------------------------- |
| `commit_hash` | Required. The commit hash you want to use as the merge base. All commits after this commit will be squashed. |
| `--lang`      | Specify the language used when generating the commit message (defaults to Chinese). |

#### Example

Suppose your commit history is as follows, and you want to merge the three commits `feat-a`, `feat-b`, `fix-c` into one.

```
* 2d3d4d5 (HEAD -> main) fix-c
* a1b2c3d feat-b
* f9e8d7c feat-a
* c1a2b3d (base-commit) initial structure  <-- This is our merge base
```

Run the following command, where `c1a2b3d` is the hash of the last commit you want to keep:

```bash
hgs c1a2b3d
```

`hgs` automatically performs the `reset` and recommit described above, and your commit history will finally become:

```
* 3e4f5g6 (HEAD -> main) feat(new-feature): add a, b and fix c
* c1a2b3d (base-commit) initial structure
```

Through these two approaches, you can continuously give HaijunBot new capabilities, enabling it to solve problems in more domains.

## 4.12 Memory System

HaijunBot has a built-in powerful memory system that helps you maintain context continuity across multiple interactions and accumulate knowledge and experience. The memory system provides its services through the two core tools `save_memory` and `retrieve_memory`.

### Memory Types

HaijunBot supports three different memory types, each with its specific purpose:

1. Short-term memory (short_term)

- Purpose: Store temporary information related to the current task
- Lifecycle: Valid only during the current session and not persisted
- Applicable scenarios: Intermediate results during task execution, temporary decisions, current context

1. Project long-term memory (project_long_term)

- Purpose: Store persistent information related to the current project
- Storage location: `.haijunbot/memory/` directory
- Applicable scenarios: Project architecture descriptions, tech stack information, project-specific conventions, API documentation, etc.

1. Global long-term memory (global_long_term)

- Purpose: Store cross-project general knowledge and preferences
- Storage location: `~/.haijunbot/memory/global_long_term/` directory
- Applicable scenarios: Programming best practices, personal preference settings, general solutions, technical notes, etc.

### Usage Examples

Save memory

```bash
# During the interaction, tell HaijunBot to save important information
hjb -T "This project uses the FastAPI framework and the database is PostgreSQL; please remember this information"
# HaijunBot automatically calls the save_memory tool and chooses the appropriate memory type

# Save a programming tip to global memory
hjb -T "Remember this Python performance optimization tip: using list comprehensions is faster than for loops"
```

Retrieve memory

```bash
# Query project-related information
hjb -T "What tech stack does this project use?"
# HaijunBot automatically retrieves the relevant information from project long-term memory

# Query programming knowledge
hjb -T "What Python performance optimization tips have I saved before?"
```

### Conversation Records

HaijunBot automatically records the entire interaction history between the user and the model, saving it as JSONL-format session files:

- **Storage location**: `~/.haijunbot/data/dialogues/` directory
- **File format**: Each session corresponds to a `.jsonl` file, with one message record per line (including timestamp, role, content, and metadata)
- **Automatic management**: The system automatically cleans up old sessions to avoid taking up too much storage space
- **Purpose**: The large model can read the session file to understand the complete conversation history, making it easy to maintain context continuity in long conversations

At the end of a session, the system indicates the save location of the session file, and you can also have the large model read that file to understand the complete conversation history.

### Advanced Usage

Batch import knowledge

```bash
# Import document content as memory
hjb -T "Please read the ./docs/api_reference.md file and save the important API information to project memory"
```

Memory association

```bash
# Establish links between related concepts
hjb -T "Remember: when using Redis caching, consider data consistency issues; you can use the publish-subscribe pattern to synchronize the cache"
```

Memory summarization

```bash
# Ask HaijunBot to summarize all relevant memories on a topic
hjb -T "Summarize all the memories I saved about database optimization"
```

By effectively using the memory system, you can make HaijunBot a truly intelligent assistant that understands you and your project, greatly improving work efficiency.

### 4.12.1 Customizing Build, Static Check, and Post-Change Configuration

In addition to using the default build system, static check tools, and formatting tools, `hca` also supports customizing the behavior of these tools through configuration files, to adapt to the special needs of different projects.

#### Customizing Build System Configuration

You can customize the behavior of the build system in the project-level configuration `.haijunbot/config.yaml`. The build validation configuration adopts a **read-write separation**: static user configuration (disabling build validation, custom build commands) is merged into the `build_validation` configuration item in config.yaml; runtime state (the asked flag, the selected build system, etc.) is automatically recorded by the program in a separate `.haijunbot/build_validation_state.yaml`.

**Configuration file locations**:

- Project-level static configuration: `.haijunbot/config.yaml` (the `build_validation` configuration item)
- Runtime state: `.haijunbot/build_validation_state.yaml` (automatically written by the program; generally no need to modify manually)

**Static configuration items** (`.haijunbot/config.yaml`):

```yaml
build_validation:
  # Custom build command (highest priority)
  custom_build_command: "make && make test"

  # Disable build validation (only perform static checks)
  disable_build_validation: false

  # Reason for disabling (optional)
  disable_reason: "The project uses a special build system"
```

**Usage examples**:

1. **Custom build command**

   If your project uses a special build process, you can specify the complete build command via `custom_build_command`:

   ```yaml
   build_validation:
     custom_build_command: "cmake -B build && cmake --build build && ctest --test-dir build"
   ```

2. **Disable build validation**

   For projects that cannot be built automatically, you can disable build validation and only perform static checks:

   ```yaml
   build_validation:
     disable_build_validation: true
     disable_reason: "The project requires specific environment variables and cannot be built automatically"
   ```

**Notes**:

- `custom_build_command` has the highest priority; if this option is set, that command is used directly for build validation
- Runtime state (such as `selected_build_system`, `has_been_asked`) is automatically recorded by the program in `.haijunbot/build_validation_state.yaml`; no manual configuration is needed
- After disabling build validation, the system still performs static checks

#### Customizing Static Check Tool Configuration

You can customize static check tools through configuration files, supporting both global configuration and project-level configuration. Project-level configuration overrides global configuration.

**Configuration file locations**:

- Global configuration: `~/.haijunbot/lint_tools.yaml`
- Project-level configuration: `.haijunbot/lint_tools.yaml`

**Configuration format**:

```yaml
# File extension/file name -> command template list
.py:
  - "ruff check {file_path}"
  - "mypy {file_path}"

.ts:
  - "eslint {file_path}"
  - "tsc --noEmit {file_path}"

.rs:
  - "cargo clippy --message-format=short"

# Matching by specific file name is also supported
dockerfile:
  - "hadolint {file_path}"
```

**Supported placeholders**:

- `{file_path}`: The full path of the file (absolute path)
- `{file_name}`: The file name (without path)
- `{config}`: The configuration file path (needs to be specified manually)

**Usage examples**:

1. **Global configuration (~/.haijunbot/lint_tools.yaml)**

   Set unified static check tools for all projects:

   ```yaml
   # Python project
   .py:
     - "ruff check {file_path}"
     - "mypy --strict {file_path}"

   # TypeScript project
   .ts:
     - "eslint {file_path}"
     - "tsc --noEmit {file_path}"
   ```

2. **Project-level configuration (.haijunbot/lint_tools.yaml)**

   Override the global configuration for a specific project:

   ```yaml
   # Use a stricter ruff configuration
   .py:
     - "ruff check {file_path} --config=pyproject.toml"
     - "mypy {file_path} --config-file=mypy.ini"

   # Add additional check tools
   .go:
     - "go vet {file_path}"
     - "golangci-lint run {file_path}"
   ```

3. **Configure project-level tools**

   Some tools (such as `cargo clippy`) do not need a file path and are project-level:

   ```yaml
   # Rust project-level tool (executed only once for the whole project)
   .rs:
     - "cargo clippy --message-format=short"
   ```

4. **Use a configuration file**

   If a tool needs a configuration file, you can specify it directly in the template:

   ```yaml
   .py:
     - "ruff check {file_path} --config=.ruff.toml"
     - "mypy {file_path} --config-file=mypy.ini"
   ```

**Notes**:

- Project-level configuration overrides items with the same name in the global configuration
- The configuration file supports two formats: a command template list `["cmd1", "cmd2"]` or a tool-template pair list `[["tool1", "cmd1"], ["tool2", "cmd2"]]`
- File name matching has higher priority than file extension matching
- For tools that do not need a file path (such as `cargo clippy`), they are executed only once per project

- File name matching has higher priority than file extension matching
- By default, post-change commands are mainly formatting tools, but you can also configure other tools (such as `eslint --fix`)

By making proper use of these configuration files, you can make `hca` perfectly adapt to the special needs of different projects and improve development efficiency.

### 4.12.2 Memory Organizer Tool (`haijunbot-memory-organizer` / `hmo`)

Over time, a large number of similar or duplicate memories may accumulate in the memory system. The `hmo` tool provides features such as organizing, merging, and importing/exporting, helping you efficiently manage the memory library.

Features

- Automatically identifies memories with similar tags and intelligently merges them
- Supports importing and exporting memories, facilitating backup and migration
- Uses AI to intelligently merge related memories, retaining all important information
- Prioritizes keeping the latest memory content (time weighting)
- Supports management of project long-term memory and global long-term memory

Subcommands

1. organize - organize and merge memories

```

Organize feature:

1. Scan all memory files of the specified type

Import/export feature:

Best Practices

- For the first organize, it is recommended to use `--dry-run` to preview the effect
- Use the import/export feature to migrate memories between different environments

## 4.13 Methodology Management (`haijunbot-methodology` / `hm`)

`hm` is the tool for managing and maintaining the HaijunBot methodology library.

### What Is a Methodology?

In HaijunBot, a Methodology is a standardized, reusable solution process for a specific Problem Type. When HaijunBot encounters a new task, it first tries to match an existing methodology. If a match is found, it refers to that methodology to make a plan, rather than thinking from scratch, thereby greatly improving the efficiency and success rate of problem-solving.

All methodologies are centered on the "problem type" and stored in independent JSON files under the `~/.haijunbot/methodologies` directory.

### Subcommands

- `import <file>`: Import methodologies from an exported JSON file; it merges with the existing methodologies (new ones override old ones with the same name).
- `export <file>`: Export all current methodologies into a single JSON file, convenient for backup and sharing.
- `list`: List the "problem types" of all current methodologies.
- `extract <file>`: From a local text file (such as a technical article or tutorial), use AI to extract and generate a new methodology.
- `extract-url <URL>`: From a web page link, use AI to read the content, extract, and generate a new methodology.

## 4.14 Security Analysis Suite (`haijunbot-sec` / `hsec`)

`hsec` is HaijunBot's security analysis suite, specifically designed for security scanning and analysis of code projects. It adopts a **configuration-driven** design philosophy, managing scan parameters through configuration files, supports heuristic scanning and AI deep verification, and can identify potential security vulnerabilities and risks.

### Core Features

- **Configuration-driven**: Manages parameters such as scan targets, language filters, and output formats through a configuration file (`.haijunbot/hsec/config.json`), facilitating reuse and version control
- **Command-line parameter override**: Supports temporarily overriding the configuration via command-line parameters in the `scan` command, flexible and convenient
- **Heuristic quick scan**: A regex-based quick scan that supports C/C++ and Rust languages, with no dependency on external services
- **AI deep analysis**: Uses an Agent to deeply analyze candidate issues and derive the complete vulnerability triggering path
- **Multi-stage verification process**: Direct scan → clustering → analysis → verification → review, ensuring result accuracy
- **Structured reports**: Generates detailed reports in JSON + Markdown/CSV format, including issue classification, severity, and fix suggestions
- **External tool integration**: Supports security analysis from the JSON output of external tools, automatically learning non-standard formats

### Workflow

```
Configuration management (hsec config) → Run scan (hsec scan) →
Direct scan (direct_scan) → Clustering (Cluster Agent) → Analysis (Analysis Agent) →
Verification (Verification Agent) → Review (Review Agent) → Report aggregation
```

1. **Configuration management**: Use the `hsec config` command to set parameters such as scan targets, language filters, excluded directories, and output formats
2. **Direct Scan**: Use predefined regex patterns to quickly identify potential security issues
3. **Clustering**: Use the LLM to cluster similar security issues, reducing duplicate analysis
4. **Analysis**: Create an independent Agent task for each candidate issue to perform deep analysis
5. **Verification**: Use an independent verification Agent to perform a second verification of the analysis results
6. **Review**: Final review and report aggregation

### Subcommands

`hsec` provides four main subcommands:

- `config`: Manage the scan configuration file
- `scan`: Run a security scan (read from the configuration file)
- `analyze`: Analyze security issues from an external JSON file
- `heuristic`: Heuristic scan (fast static analysis, no AI deep verification needed)

#### `config` - Manage the Configuration File

The configuration file is located at `.haijunbot/hsec/config.json` and contains the following main configuration items:

- `target`: Scan target (a file path or directory path)
- `languages`: Language filter list (such as `c`, `cpp`, `rust`)
- `exclude_dirs`: List of directories to exclude
- `output`: Output configuration (format and file)
- `analysis`: Analysis parameters (cluster_limit, enable_verification, force_save_memory)
- `runtime`: Runtime configuration (llm_group)

**Parameters**:

| Parameter                         | Description                                                          |
| --------------------------------- | -------------------------------------------------------------------- |
| `--target <path>`                 | Set the scan target (a file path or directory path)                  |
| `--languages <language_list>`     | Set the language filter (comma-separated, e.g., c,cpp,rust)          |
| `--exclude-dirs <directory_list>` | Set the excluded directories (comma-separated)                       |
| `--output-format <format>`        | Set the output format (csv/markdown)                                 |
| `--output-file <path>`            | Set the output file path                                             |
| `--cluster-limit <count>`         | Set the clustering limit (maximum number of alerts processed per batch) |
| `--enable-verification/--no-verification` | Whether to enable the second-pass verification               |
| `--force-save-memory/--no-force-save-memory` | Whether to force the use of memory                          |
| `--llm-group <group_name>`        | Set the model group                                                  |
| `--show`                          | Show the current configuration                                        |
| `--clear`                         | Clear the configuration (reset to defaults)                          |

**Usage examples**:

```bash
# Set the scan target to the current directory
hsec config --target .

# Set the scan target to a specified directory
hsec config --target ./src

# Set the scan target to a specified file
hsec config --target ./src/main.c

# Set the language filter and output format
hsec config --languages c,cpp,rust --output-format csv

# Set analysis parameters
hsec config --cluster-limit 30 --enable-verification

# Set the model group
hsec config --llm-group deep_seek_v3

# View the current configuration
hsec config --show

# Clear the configuration
hsec config --clear
```

#### `scan` - Run a Security Scan

Reads all configuration from the configuration file and runs the scan. If the configuration file does not exist, a friendly prompt guides the user to use the `config` command.

**Supported scan modes**:
- **Directory scan**: Scans all files under the specified directory
- **File scan**: Scans the specified file (scans the directory where the file is located, then filters to keep only that file's issues)

**Usage examples**:

```bash
# Run the scan (using the settings in the configuration file)
hsec scan

# Complete flow of configuring and scanning
# 1. Set the scan target
hsec config --target ./src

# 2. Set the output format
hsec config --output-format markdown --output-file report.md

# 3. Run the scan
hsec scan

# Scan a single file
hsec config --target ./src/main.c
hsec scan
```

#### `analyze` - Analyze an External JSON File

Performs security analysis from the JSON output of an external scanning tool and supports automatically learning non-standard formats.

**Parameters**:

| Parameter                         | Description                                                          |
| --------------------------------- | -------------------------------------------------------------------- |
| `input`                           | Path to the external JSON file (required parameter)                  |
| `--output-format <format>`        | Output format (csv/markdown)                                         |
| `--output-file <path>`            | Output file path                                                     |
| `--cluster-limit <count>`         | Clustering limit (maximum number of alerts processed per batch, default 50) |
| `--enable-verification/--no-verification` | Whether to enable the second-pass verification (enabled by default) |
| `--force-save-memory/--no-force-save-memory` | Whether to force the use of memory (disabled by default) |

**Example of the standard format**:

```json
{
    "issues": [
        {
            "language": "c",
            "category": "memory",
            "pattern": "strcpy",
            "file": "src/main.c",
            "line": 42,
            "evidence": "strcpy(dest, src)",
            "description": "Unsafe string copy",
            "suggestion": "Use strncpy instead",
            "confidence": 0.8,
            "severity": "high"
        }
    ]
}
```

**Usage examples**:

```bash
# Analyze a file in the standard format
hsec analyze external_issues.json

# Analyze a file in a non-standard format (automatically converted)
hsec analyze custom_tool_output.json

# Specify the output format
hsec analyze issues.json --output-format csv --output-file report.csv

# Disable the second-pass verification (fast mode)
hsec analyze issues.json --no-verification

# Adjust the clustering batch size
hsec analyze issues.json --cluster-limit 100
```

### Output Description

`hsec` generates the following outputs:

- **Markdown report** (default): a human-readable detailed report, including issue descriptions, severity, and fix suggestions
- **CSV report** (when configured for csv format): a structured CSV-format report, easy to import into tools such as Excel for analysis
- **Console output**: real-time output of the analysis process and a summary of the final report

### Notes

- For first use, you need to run `hsec config` first to configure the scan parameters
- The first run may take a long time, especially for large codebases
- It is recommended to integrate it into the CI/CD pipeline and run security scans periodically
- False positives can be filtered through the review process
- Security analysis supports C/C++ and Rust languages
- If the Agent analysis process errors or produces no output, it automatically falls back to the direct-scan baseline (fast mode)
- When analyzing external tool output with the `analyze` command, if the format does not conform to the standard, the system automatically creates an Agent to learn the format and convert it

## 4.15 C→Rust Migration Suite (`haijunbot-c2rust` / `hc2r`)

`hc2r` is HaijunBot's C→Rust migration suite, specifically designed to intelligently migrate C/C++ code to Rust. It adopts a gradual migration strategy and supports resuming from checkpoints, ensuring the migration process is safe and controllable.

### Core Features

- **Intelligent code scanning**: Precise AST parsing based on libclang, extracting functions, types, and call relationships
- **Library replacement evaluation**: Uses the LLM to evaluate whether a C function can be replaced by the Rust standard library or a third-party crate
- **Module planning**: Uses an Agent to intelligently plan the module structure of the Rust crate
- **Code transpilation**: Uses CodeAgent for code generation and repair, supporting dependency checks and automatic implementation
- **Conservative optimization**: Optimizes while ensuring code correctness
- **Gradual migration**: Supports resuming from checkpoints, allowing the migration to be completed in batches
- **Rollback mechanism**: Build detection and git_guard ensure the migration process is reversible

### Workflow

```
Scan (scan) → Library replacement (lib-replace) → Module planning (prepare) →
Transpile (transpile) → Optimize (optimize)
```

1. **Scan (scan)**: Use libclang to parse the C/C++ code and generate a symbol table and call graph
2. **Library replacement (lib-replace)**: Evaluate which C functions can be replaced with Rust libraries
3. **Module planning (prepare)**: Use an Agent to plan the module structure of the Rust crate
4. **Transpile (transpile)**: Use CodeAgent for code generation and repair
5. **Optimize (optimize)**: Perform conservative optimization while ensuring correctness

### Subcommands

`hc2r` provides three main subcommands:

#### 1. `config` - Manage the Transpilation Configuration File

Manages the transpilation configuration file (`.haijunbot/c2rust/config.json`). You can set the root symbol list, the disabled libraries list, and additional notes.

**Parameters**:

| Parameter                    | Description                                                                             |
| ---------------------------- | --------------------------------------------------------------------------------------- |
| `--files <files...>`         | Header files (.h/.hh/.hpp/.hxx) or a function-name list file (one function name per line, ignoring blank lines and comments starting with #) |
| `--root-list-syms <symbol_list>` | Inline root symbol list (comma-separated)                                           |
| `--disabled-libs <lib_list>` | Disabled libraries list (comma-separated)                                               |
| `--additional-notes <notes>` | Additional notes (appended to the prompt of all agents)                                 |
| `--show`                     | Show the current configuration content                                                  |
| `--clear`                    | Clear the configuration (reset to defaults)                                             |

**Usage examples**:

```bash
# Automatically extract function names from header files and set the root symbol list
hc2r config --files bzlib.h

# Extract function names from multiple header files
hc2r config --files a.h b.hpp c.hxx

# Set the root symbol list from a function-name list file
hc2r config --files roots.txt

# Set the root symbol list from the command line
hc2r config --root-list-syms "func1,func2,func3"

# Set the disabled libraries list
hc2r config --disabled-libs "libc,libm"

# Set additional notes
hc2r config --additional-notes "Note: all functions must handle error cases and avoid panics"

# Set multiple parameters at once
hc2r config --files bzlib.h --disabled-libs "libc" --additional-notes "Special requirements note"

# View the current configuration
hc2r config --show

# Clear the configuration
hc2r config --clear
```

#### 2. `run` - Run the Complete Transpilation Pipeline

Runs the pipeline in sequence: scan → lib-replace → prepare → transpile → optimize, with support for resuming from checkpoints.

**Parameters**:

| Parameter                   | Description                                                          |
| --------------------------- | ------------------------------------------------------------------- |
| `-g/--llm-group <group_name>` | The model group for the LLM-related stages (lib-replace/prepare/transpile/optimize) |
| `-m/--max-retries <count>` | The maximum number of retries for transpile build/repair and review (0 means unlimited) |
| `--interactive`             | Enable interactive mode (non-interactive by default)                |
| `--reset`                   | Reset the state and run all stages from the beginning               |
| `--quick-mode`              | Quick mode, disabling methodology and rule loading, etc.            |

**Usage examples**:

```bash
# Run the complete transpilation pipeline (using the default configuration)
hc2r run

# Specify the model group
hc2r run -g deep_seek_v3

# Set the maximum number of retries
hc2r run -m 3

# Enable interactive mode
hc2r run --interactive

# Reset the state and run from the beginning
hc2r run --reset

# Combine multiple parameters
hc2r run -g deep_seek_v3 -m 5 --interactive
```

#### 3. `verify` - Verify Functional Alignment

Verifies the functional alignment between the transpiled Rust code and the original C code, and supports iterative optimization. The transpile and optimize stages of `run` must be completed first.

**Parameters**:

| Parameter                    | Description                              |
| ---------------------------- | ---------------------------------------- |
| `-g/--llm-group <group_name>` | The model group for LLM analysis and optimization |
| `-i/--max-iterations <count>` | Maximum number of iterations (default 10) |
| `--interactive`              | Enable interactive mode (non-interactive by default) |
| `--quick-mode`               | Quick mode, disabling methodology and rule loading, etc. |

**Usage examples**:

```bash
# Run the functional alignment verification
hc2r verify

# Specify the model group and maximum number of iterations
hc2r verify -g deep_seek_v3 -i 5
```

### Checkpoint Resume Mechanism

`hc2r run` supports resuming from checkpoints and automatically skips completed stages based on the state file (`.haijunbot/c2rust/run_state.json`):

- If a stage is already completed, it is automatically skipped and the next stage is continued
- Using `--reset` resets the state and runs all stages from the beginning
- The state file records the completion status and timestamp of each stage

### Configuration File Description

The transpilation configuration is saved in `.haijunbot/c2rust/config.json` and includes:

- **root_symbols**: The root symbol list, used to determine the entry functions for transpilation
- **disabled_libraries**: The disabled libraries list, specifying which libraries are not used for replacement
- **additional_notes**: Additional notes, appended to the prompt of all agents

### Technical Features

- **Precise parsing**: Uses libclang to provide accurate AST parsing, preserving complete type information
- **Dependency management**: Automatically extracts function call relationships, ensuring the transpilation order follows the dependency relationships
- **Test protection**: Based on an event subscription mechanism, ensuring test code is not accidentally deleted
- **Memory saving**: The code generation Agent enables forced memory saving to record key information
- **Dependency checking**: Automatically checks and fills in the implementation of dependent functions when implementing a function

### Output Description

`hc2r` generates the following files under the `.haijunbot/c2rust/` directory:

- **symbols.jsonl**: The unified symbol table (the main input for subsequent processes)
- **symbols_raw.jsonl**: The raw symbol table
- **translation_order.jsonl**: The order in which functions are transpiled
- **library_replacements.jsonl**: The library replacement mapping relationships
- **run_state.json**: The run state file (used for resuming from checkpoints)
- **config.json**: The transpilation configuration file
- **symbol_map.jsonl**: The symbol mapping relationships

### Notes

- libclang (clang.cindex) needs to be installed; libclang versions 16-21 are supported
- It is recommended to use compile_commands.json to improve parsing accuracy
- The migration process automatically performs build detection to ensure the code compiles
- Batch transpilation of large-scale projects is supported, and can be interrupted and continued later
- The migrated code requires manual review and testing
- The root symbol list and disabled libraries list must first be set via the `config` command

## 4.16 Tmux Task Dispatch System

HaijunBot provides a tmux task dispatch feature that can dispatch tasks to new tmux panes for execution. **You need to set `enable_tmux: true` in the configuration to use it**. It is suitable for scenarios where you need to separate tasks into independent panes or monitor long-running tasks.

### 4.16.1 Core Features

The tmux task dispatch system provides the following core features:

1. **Task dispatch**: Dispatches a task to a new tmux pane for execution, allowing the main session to continue with other operations
2. **Automatic session management**: Automatically detects and manages tmux sessions, without the need to start them manually
3. **Layout optimization**: Automatically adjusts the pane layout to `tiled` mode, optimizing the display effect
4. **Fallback support**: When not in a tmux environment, it finds or creates a HaijunBot session as a fallback

### 4.16.2 Basic Usage

#### Using the --dispatch Parameter

The most direct way is to use the `--dispatch` or `-d` parameter in a supported command:

```bash
# Dispatch a general-purpose agent task to a new tmux pane
hjb --dispatch --task "Analyze the security issues of the current project"

# Dispatch a code agent task to a new tmux pane
hca --dispatch --task "Refactor the code under the src/utils directory"

# Use the short parameter form
hjb -d -T "Check for potential errors in the code"
```

When the `--dispatch` parameter is used, the task starts in a new tmux pane and the main process exits immediately, allowing you to continue performing other operations in the original pane.

### 4.16.3 Dedicated Dispatch Tools

HaijunBot provides dedicated dispatch tools to improve ease of use:

#### hjbd - HaijunBot Agent Dispatcher

`hjbd` is the convenient dispatch tool for the general-purpose agent, dedicated to task dispatch:

```bash
# Dispatch a task directly
hjbd "Analyze the current project structure and generate a report"

# Enter a task in interactive mode (confirm with Ctrl+J)
hjbd
```

#### hcad - HaijunBot Code Agent Dispatcher

`hcad` is the convenient dispatch tool for the code agent:

```bash
# Dispatch a code task directly
hcad "Refactor the user authentication module, using a new encryption algorithm"

# Enter a code task in interactive mode
hcad
```

These two tools automatically enable non-interactive mode (`-n`), worktree mode (`--worktree`, for hcad), and task dispatch (`--dispatch`), simplifying the startup process for parallel tasks.

### 4.16.4 Advanced Usage

#### Task File Support

Besides entering a task directly, you can also read the task content from a file:

```bash
# Create the task file
cat > my_task.txt << EOF
Task description: refactor the user management module
1. Extract the user validation logic into an independent service class
2. Implement a caching mechanism for user permissions
3. Add audit logs for user operations
Background: users report that the current module responds slowly
EOF

# Dispatch the task file
hjbd < my_task.txt
```

#### Worktree Mode (hca only)

When using `hcad`, Git worktree mode is automatically enabled, ensuring the task is developed on an independent branch to avoid conflicts with the main branch:

```bash
# Execute a code task in an independent worktree
hcad "Implement the new payment feature"
```

Git worktree mode is a powerful development mode provided by HaijunBot, allowing development on an independent branch to avoid conflicts with the main branch.

##### Core Features

1. **Isolated development**: Develop on an independent branch without affecting the stability of the main branch
2. **Automatic branch management**: Automatically creates and cleans up worktree branches, and supports automatic creation of the repository's initial commit
3. **Symlink support**: Automatically symlinks the original repository's `.haijunbot` directory into the worktree, ensuring consistency of configuration and data
4. **Automatic commit of unsaved changes**: In worktree mode, uncommitted code changes are automatically handled, ensuring the working tree is clean before task execution
5. **Intelligent merge**: Uses the rebase strategy to merge the worktree branch back to the original branch, keeping a linear history

##### Usage

The `hcad` command enables worktree mode by default, ensuring code modifications are performed on an independent branch:

```bash
# Execute a code task in an independent worktree
hcad "Implement the new payment feature"

# Use worktree in interactive mode
hcad
# Then enter the task description
```

For the `hca` command, worktree mode can also be enabled via the `--worktree` parameter:

```bash
# Enable worktree mode to execute a code task
hca --worktree -T "Refactor the user authentication module, using a new encryption algorithm"
```

##### Workflow

1. **Create the worktree**: The system automatically generates a unique branch name (format: `haijunbot-{project_name}-{timestamp}-{random_suffix}`) and creates a git worktree on that branch. If the repository does not yet have an initial commit, one is created automatically
2. **Link configuration**: Symlink the original repository's `.haijunbot` directory into the worktree
3. **Automatically commit unsaved changes**: If uncommitted code changes are detected, they are automatically committed, ensuring the working tree is clean before task execution
4. **Execute the task**: Perform the code modification task in the worktree directory
5. **Merge back to the main branch**: After the task is completed, use the rebase strategy to rebase the worktree branch onto the original branch, then merge via fast-forward
6. **Clean up resources**: Automatically delete the worktree directory and the corresponding branch

##### Branch Naming Convention

Worktree branches use the following naming format:

```
haijunbot-{project_name}-{YYYYMMDD}-{HHMMSS}-{4 random characters}
```

For example: `haijunbot-myproject-20231201-143052-abcd`

This naming approach ensures the uniqueness of branch names and avoids naming conflicts.

##### Security Mechanisms

1. **Path safety verification**: When creating symlinks, the system verifies that the target path is under the worktree directory, preventing directory traversal attacks
2. **Conflict handling**: When merging branches, if a conflict occurs, the system prompts the user to resolve it manually
3. **State check**: Before merging, the main repository state is checked to ensure it is clean, avoiding accidental modifications being merged

### 4.16.5 Notes

1. **Enable/disable tmux**: Use the `enable_tmux` configuration item to control whether the tmux features are enabled

   ```yaml
   # config.yaml
   enable_tmux: false # Defaults to false; set to true to enable tmux
   ```

   When set to `false`, the system disables all tmux-related features, including automatically starting tmux sessions and dispatching tasks to tmux windows. This is especially useful for users who do not want to use tmux.

2. **tmux installation**: Make sure tmux is installed on the system

   ```bash
   # Ubuntu/Debian
   sudo apt install tmux
   # CentOS/RHEL
   sudo yum install tmux
   # macOS
   brew install tmux
   ```

3. **Automatic startup**: When not in a tmux environment but the `--dispatch` parameter is used, the system automatically creates a new tmux session and executes the task

4. **Resource management**: Dispatched tasks consume additional system resources; schedule them reasonably according to system capabilities

5. **Session management**: Dispatched tasks run in independent panes; you can use tmux commands (such as `tmux attach`) to manage the sessions

## 4.17 Configuration Management Tool (`haijunbot-config` / `hcfg`)

`haijunbot-config` is HaijunBot's configuration management tool. It dynamically generates configuration Web pages based on JSON Schema, providing a friendly visual configuration interface that makes configuration management simple and intuitive.

### Core Features

- **Dynamic Web interface**: Automatically generates form pages according to the JSON Schema, without the need to write configuration files manually
- **Real-time validation**: Schema-based real-time configuration validation, ensuring configuration correctness
- **Visual operations**: Configure through the browser interface, supporting various form controls such as dropdowns, switches, and text inputs
- **Flexible configuration**: Supports custom Schema files and output paths, suitable for different scenarios
- **Automatic saving**: Automatically saves the configuration in YAML format after completion, compatible with HaijunBot's configuration system

### Common Parameters

| Parameter                | Description                                                |
| ------------------------ | ---------------------------------------------------------- |
| `--schema`, `-s`         | JSON Schema file path (default: HaijunBot's config_schema.json) |
| `--output`, `-o`         | Output configuration file path (default: ~/.haijunbot/config.yaml) |
| `--port`, `-p`           | Web service port (default: 8080)                           |
| `--no-browser`, `/nb`    | Do not automatically open the browser after startup        |

### Examples

1. Default configuration
   Start the Web interface with the default configuration, automatically using HaijunBot's config_schema.json and outputting to ~/.haijunbot/config.yaml:

```bash
haijunbot-config
```

1. Custom Schema file
   Use a custom JSON Schema file to generate the configuration page:

```bash
haijunbot-config --schema custom.json
```

1. Specify the output path
   Save the configuration to the specified path:

```bash
haijunbot-config --output /path/to/custom_config.yaml
```

1. Custom port
   Start the Web service on the specified port:

```bash
haijunbot-config --port 3000
```

1. Do not automatically open the browser
   Start the service without automatically opening the browser:

```bash
haijunbot-config --no-browser
```

1. Combine multiple parameters
   Complete example: use a custom Schema, output path, and port:

```bash
haijunbot-config -s my_schema.json -o my_config.yaml -p 9000 --no-browser
```

### Workflow

1. **Start the service**: Run the `haijunbot-config` command, and the system generates the Web configuration page according to the specified JSON Schema file
2. **Access via browser**: By default, the configuration page is automatically opened in the browser (e.g. <http://localhost:8080）>
3. **Fill in the configuration**: Fill in each configuration item in the Web interface; the form automatically generates the corresponding input controls according to the Schema
4. **Real-time validation**: Input is validated in real time against the Schema, ensuring the configuration format is correct
5. **Save the configuration**: Click the save button, and the system automatically saves the configuration as a YAML file
6. **Stop the service**: Press Ctrl+C to stop the Web service

### Applicable Scenarios

- **Initial configuration**: When using HaijunBot for the first time, complete the configuration quickly through the visual interface
- **Configuration migration**: When migrating from an old version to a new version, use the new Schema to generate the configuration
- **Team configuration**: Provide a unified configuration template for team members, ensuring configuration consistency
- **Complex configuration**: For complex configuration items, the visual interface is more intuitive than manually editing YAML
- **Custom scenarios**: Create custom configuration pages for specific projects or applications
````
