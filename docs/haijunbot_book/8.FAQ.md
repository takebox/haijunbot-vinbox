# 8. Frequently Asked Questions (FAQ)

This chapter collects some of the most common questions encountered by users when using HaijunBot, along with their solutions.

---

## Q1: In multi-line input mode, why can't I submit by pressing Enter?

**A1:** This is because in multi-line input mode, HaijunBot designs the Enter key to input a newline character, so that users can conveniently enter multi-line text (such as pasting code, writing detailed descriptions, etc.).

**Solution:**
Use the `Ctrl + J` shortcut to submit your multi-line input. This shortcut hint is usually displayed above the multi-line input box.

## Q2: How do I use a custom OpenAI endpoint (API Base URL)?

**A2:** Specify a custom OpenAI endpoint address by setting the environment variable `OPENAI_API_BASE`. HaijunBot uses the official address `https://api.openai.com/v1` by default; if you use a proxy or a third-party service, set it to the corresponding Base URL.

**Example setup methods:**

- Linux/macOS (Bash/Zsh):
  - Temporary setting (valid for the current terminal session):
    - `export OPENAI_API_BASE="https://your-proxy.example.com/v1"`
  - Permanent setting (write to a shell config file such as ~/.bashrc or ~/.zshrc):
    - Add the above `export` line to the config file and reload or restart the terminal
- Windows PowerShell:
  - Current session: `"$env:OPENAI_API_BASE = 'https://your-proxy.example.com/v1'"`

**Notes:**

- After changing the environment variable, restart HaijunBot for the configuration to take effect.
- `OPENAI_API_BASE` only affects the request address for the OpenAI platform and does not affect other platforms.

## Q3: How do I pass custom HTTP headers to the OpenAI client?

**A3:** Set the environment variable `OPENAI_EXTRA_HEADERS` to a JSON object, and HaijunBot will pass it as default HTTP headers when initializing the OpenAI client (if the current SDK version does not support it, a warning will be given but basic functionality will not be affected).

**Example:**

- Linux/macOS (recommended to wrap in single quotes to avoid escaping issues):
  - `export OPENAI_EXTRA_HEADERS='{"User-Agent":"HaijunBot/1.0","X-Source":"haijunbot"}'`
- Windows PowerShell:
  - `"$env:OPENAI_EXTRA_HEADERS = '{\"User-Agent\":\"HaijunBot/1.0\",\"X-Source\":\"haijunbot\"}'"`

**Notes:**

- The value of `OPENAI_EXTRA_HEADERS` must be a JSON object (in the form `{"Key":"Value"}`); keys and values are treated as strings.
- To cancel custom headers, delete or clear the environment variable (on Linux/macOS you can use `unset OPENAI_EXTRA_HEADERS`).
- Common uses include: customizing the User-Agent, adding tracing headers (such as `X-Trace`), and satisfying the extra authentication requirements of enterprise proxies, etc.

## Q4: How do I configure multiple models and switch between them in different scenarios?

**A4:** HaijunBot supports configuring multiple model groups via `llm_groups` and switching via `llm_group`.

**Configuration method:**

Define model groups in `~/.haijunbot/config.yaml`:

```yaml
# 1. Define reusable model configurations
llms:
  gpt-5:
    platform: openai
    model: gpt-5
    max_input_token_count: 128000
    llm_config:
      openai_api_key: "your-api-key"
  haijun-4:
    platform: openai
    model: haijun-opus-4-5-20251101
    max_input_token_count: 200000
    llm_config:
      openai_api_key: "your-api-key"

# 2. Define model groups
llm_groups:
  power:
    normal_llm: haijun-4
    cheap_llm: gpt-5
    fallback_group: speed  # Optional: in non-interactive mode, automatically switch to the speed group when the power group fails consecutively
  speed:
    normal_llm: gpt-5

# 3. Select the model group to use
llm_group: power
```

**Usage:**

- Via the configuration file: change the value of `llm_group`
- Via the command line: use the `-g` or `--llm-group` parameter to switch temporarily, e.g. `hjb -g speed`

**Automatic failover (fallback model group):**

A model group can specify a fallback group via the optional `fallback_group`. When the models in the current group fail consecutively (retries are exhausted and an empty result is still returned), HaijunBot will automatically switch to the fallback group and retry once. Note:

- This only takes effect in **non-interactive mode**; no automatic switching occurs in interactive mode;
- No switching occurs when `fallback_group` is not configured;
- It only switches once; if it still fails after switching, it will not continue to switch to other groups.

## Q5: What should I do if a tool is not loaded or cannot be found?

**A5:** Tool loading failures are usually caused by the following reasons:

**Possible causes and solutions:**

1. **File name does not match the tool name**
   - Check whether the tool file name (without the `.py` suffix) is exactly the same as the `name` attribute in the class
   - For example: the class in the file `my_tool.py` must have `name = "my_tool"`

2. **Incorrect tool file location**
   - Check whether the tool file is in the correct directory:
     - User tools: `~/.haijunbot/tools/`
     - Extra directories: the directories specified by the `tool_load_dirs` configuration
     - Central tool repository: the repository specified by the `central_tool_repo` configuration

3. **Tool class is missing required attributes**
   - Make sure the tool class contains: the `name`, `description`, and `parameters` attributes and the `execute` method

4. **Incorrect tool loading directory configuration**
   - Check whether the `tool_load_dirs` configuration is correct (list format)
   - Check whether the path is correct (`~` and environment variable expansion are supported)

5. **Viewing the tool list**
   - Use the `ht list` command to view all loaded tools
   - Use `ht list --detailed` to view detailed information

## Q6: What should I do if a rule is not loaded or does not take effect?

**A6:** Rule loading problems may be caused by the following reasons:

**Possible causes and solutions:**

1. **Incorrect rule file location**
   - Global rules: `.md` files in the `~/.haijunbot/rules/` directory
   - Project rules: `.md` files in the `.haijunbot/rules/` directory
   - Configured rule directories: the directories specified by `rules_load_dirs`

2. **Rule name does not match**
   - When using `--rule-names`, make sure the rule name exactly matches the file name (including the relative subdirectory path, which may carry prefixes such as `project:`/`global:`/`central:`) (case-sensitive)

3. **Rule loading priority**
   - Check whether a rule with the same name is overridden by a higher-priority source
   - Priority order: central rules repository > project rules directory > global rules directory > configured rules directory > built-in rules

4. **Incorrect rule format**
   - Rule files should be in Markdown (`.md`) format, and may optionally use YAML Front Matter to declare metadata such as `description`
   - Note: HaijunBot does not support a format like `rules.yaml` where "a single YAML file defines multiple named rules"

5. **Central rules repository not configured**
   - If you use a central rules repository, make sure `central_rules_repo` is configured correctly
   - Check whether the repository has been successfully cloned to `~/.haijunbot/central_rules_repo`

## Q7: How do I configure and use custom tool groups?

**A7:** Via the `tool_groups` configuration you can define different tool sets and switch between them when needed.

**Configuration method:**

```yaml
# ~/.haijunbot/config.yaml

# 1. Define tool groups
tool_groups:
  - coding: # Code development group
      use: # Only use these tools
        - execute_script
        - read_code
        - edit_file
        - save_memory
  - document: # Document processing group
      use:
        - save_memory
        - retrieve_memory
  - restricted: # Restricted group (read-only)
      use:
        - read_code

# 2. Select the tool group to use
tool_group: coding
```

**Usage:**

- Via the configuration file: change the value of `tool_group`
- Via the command line: use the `-G` or `--tool-group` parameter to switch temporarily, e.g. `hjb -G restricted`

**Notes:**

- If a `use` list is configured, only the tools in the list are available
- If a `dont_use` list is configured, the tools in the list are excluded
- If the same tool appears in both `use` and `dont_use`, it will ultimately be excluded (first kept according to `use`, then removed according to `dont_use`)
- By default (with no tool group set), all tools are available

## Q8: How do I configure MCP tools?

**A8:** MCP (Model Context Protocol) tools are configured via the `mcp` configuration list.

**Configuration method:**

Add the `mcp` configuration in `~/.haijunbot/config.yaml`:

```yaml
mcp:
  # stdio type: local command-line program
  - type: "stdio"
    name: "my_cli_tools"
    command: "/path/to/your/tool_program"
    args: ["--json-rpc"]
    env:
      CUSTOM_VAR: "value"
    enable: true

  # sse type: Server-Sent Events remote service
  - type: "sse"
    name: "realtime_service"
    base_url: "https://api.example.com/mcp"
    auth_token: "your-secret-token"
    headers:
      X-Custom-Header: "value"
    enable: true

  # streamable type: streaming HTTP service
  - type: "streamable"
    name: "large_file_processor"
    base_url: "https://stream.example.com/api"
    auth_token: "your-secret-token"
    endpoint_path: "mcp" # Optional, defaults to "mcp"
    timeout: [10, 300] # Optional, [connection timeout, read timeout] in seconds
    enable: true
```

**Notes:**

- Each MCP configuration must contain the `type` field
- The `name` field is optional, but it is recommended to specify a unique name for each configuration
- The `enable` field is optional and defaults to `true`
- **sse/streamable types**: `base_url` must be provided; `auth_token`, `headers`, `endpoint_path` (streamable only), and `timeout` (streamable only) are optional
- **stdio type**: `command` must be provided; `args` and `env` are optional
- Restart HaijunBot after configuration for it to take effect
- You can use `ht list` to check whether MCP tools are loaded successfully

## Q9: How do I configure a central repository (methodologies, tools, rules)?

**A9:** The central repository configuration allows teams to share resources, supporting automatic cloning and daily updates.

**Configuration method:**

Add the following in `~/.haijunbot/config.yaml`:

```yaml
# Central methodology repository
central_methodology_repo: "https://github.com/your-org/haijunbot-methodologies.git"

# Central tool repository
central_tool_repo: "https://github.com/your-org/haijunbot-tools.git"

# Central rules repository
central_rules_repo: "https://github.com/your-org/haijunbot-rules.git"
```

**How it works:**

1. On first use, HaijunBot automatically clones the repository to the data directory
2. On each daily startup, `git pull` is automatically executed to update the latest content (only effective for users who installed HaijunBot via `uv tool`)
3. Resources are loaded by priority (the central repository has the highest priority)

**Sharing resources to the central repository:**

```bash
# Share methodology
haijunbot --share-methodology

# Share tool
haijunbot --share-tool

# Share rule
haijunbot --share-rule
```

**Notes:**

- The central repository supports a local directory path or a Git URL
- If it is a Git URL, it will be automatically cloned into the `~/.haijunbot/` directory
- If it is a local directory, that directory will be used directly
- Methodology and rules sharing is a **copy** (the original file is kept), while tool sharing is a **move** (the original file will be deleted)

## Q10: How do I migrate between the new configuration approach (llm_groups/llms) and the old configuration approach (platform/model)?

**A10:** HaijunBot supports two configuration approaches; it is recommended to use the new one for greater flexibility.

**New configuration approach (recommended):**

```yaml
llms:
  my_model:
    platform: openai
    model: gpt-5
    max_input_token_count: 128000
    llm_config:
      openai_api_key: "your-key"

llm_groups:
  default:
    normal_llm: my_model

llm_group: default
```

**Old configuration approach (still supported):**

```yaml
platform: openai
model: gpt-5
ENV:
  OPENAI_API_KEY: "your-key"
```

**Migration steps:**

1. Define the model configuration in `llms`
2. Create a model group in `llm_groups`, referencing the configuration in `llms`
3. Set `llm_group` to select the group to use
4. The old `platform` and `model` configuration can be kept as a fallback, but it is recommended to migrate to the new approach

**Note:** The new configuration approach provides more flexible model management, supporting the definition of multiple model groups and switching between them in different scenarios.

## Q11: How do I debug HaijunBot's behavior?

**A11:** HaijunBot provides several debugging options to help diagnose problems.

**Debugging methods:**

1. **Print the full prompt (Prompt)**

   ```yaml
   # ~/.haijunbot/config.yaml
   print_prompt: true
   ```

   After enabling, the full prompt sent to the LLM will be printed in the terminal, for debugging model input.

2. **Print the error traceback**

   ```yaml
   # ~/.haijunbot/config.yaml
   print_error_traceback: true
   ```

   After enabling, the full call stack will be automatically printed when an error is output.

3. **View the tool list**

   ```bash
   # View all tools
   ht list

   # View detailed information
   ht list --detailed
   ```

4. **View tool usage statistics**

   ```bash
   ht stat
   ```

5. **View the configuration**

   ```bash
   # Edit the configuration file
   hjb -e

   # Or view directly
   cat ~/.haijunbot/config.yaml
   ```

6. **View sessions and exception records**
   - Session files: `.haijunbot/sessions/` in the current working directory (each session generates a separate session file)
   - Exception records: the `~/.haijunbot/exceptions/` directory (a detailed stack is saved when an exception occurs)

## Q12: How do I solve the problem of the "tool execution confirmation" popping up frequently?

**A12:** If `execute_tool_confirm` is enabled, confirmation is required before each tool execution.

**Solution:**

1. **Disable tool execution confirmation**

   ```yaml
   # ~/.haijunbot/config.yaml
   execute_tool_confirm: false
   ```

2. **Use tool groups to limit tools**
   By configuring `tool_groups`, only enable the necessary tools, reducing the number of tools that require confirmation.

3. **Use non-interactive mode**
   Use the `-n` or `--non-interactive` parameter in automation scenarios, which will automatically handle confirmation.

**Note:** `execute_tool_confirm` is a security feature; before disabling it, make sure you understand the commands that will be executed.

## Q13: How do I set OpenAI's reasoning effort (Reasoning Effort)?

**A13:** OpenAI's o1 series models support controlling the reasoning effort via the `reasoning_effort` parameter, which affects the model's thinking and answer quality.

**Setting method:**

Set via an environment variable:

- Linux/macOS:
  - `export OPENAI_REASONING_EFFORT="medium"`
- Windows PowerShell:
  - `$env:OPENAI_REASONING_EFFORT = "medium"`

Or set via the configuration file:

```yaml
# ~/.haijunbot/config.yaml
llms:
  o1-model:
    platform: openai
    model: o1-preview
    llm_config:
      openai_api_key: "your-api-key"
      openai_reasoning_effort: "medium" # Optional values: low, medium, high, xhigh
```

**Optional values:**

- `low`: lowest reasoning effort, fast response time
- `medium`: medium reasoning effort
- `high`: high reasoning effort, deeper thinking
- `xhigh`: highest reasoning effort, suitable for complex problems

> If not set, HaijunBot will not pass the `reasoning_effort` parameter to the interface; the model/server will adopt its default behavior.

## Q15: How do I configure login authentication for the Web Gateway?

**A15:** The Web Gateway uses a built-in multi-user authentication system (username + password); after a successful login it issues a JWT Token for subsequent requests.

**User data storage:**

User information is stored in `auth/users.json` under the gateway data directory (i.e. `<data directory>/auth/users.json`), and passwords are stored using bcrypt hashing.

**First startup:**

On first startup, if no admin user exists, an `admin` user is automatically created:

- If the environment variable `HAIJUNBOT_ADMIN_PASSWORD` is set, its value is used as the initial password;
- Otherwise, a random 16-digit hexadecimal password is generated and written to the log (please check the startup log).

```bash
# It is recommended to explicitly specify the admin initial password before the first startup
export HAIJUNBOT_ADMIN_PASSWORD="your-secure-password"
```

**Login method:**

The frontend submits `{"username": "...", "password": "..."}` via `POST /api/auth/login`; upon successful verification it returns a JWT Token; subsequent requests must carry this Token (Bearer). Reaching the upper limit of consecutive login failures (5 times) triggers account lockout.

**Notes:**

- Users are created/managed by the administrator in the Web interface (supporting password change, password reset, disable, etc.)
- At least one administrator user must be retained; deleting the last administrator is not allowed
- It is recommended to use strong passwords and change them regularly

## Q16: How do I configure multiple API Keys for round-robin use?

**A16:** API Keys now support configuring multiple keys, which are automatically used in a round-robin manner on requests; this is suitable for scenarios that need to distribute request pressure or avoid rate limiting on a single Key.

**Configuration methods:**

### Method 1: Configure via llm_config (recommended)

**List format:**

```yaml
# ~/.haijunbot/config.yaml
llms:
  gpt-5:
    platform: openai
    model: gpt-5
    llm_config:
      openai_api_key: ["sk-key1", "sk-key2", "sk-key3"] # Multiple keys list, automatically polled
```

**Comma-separated format:**

```yaml
llm_config:
  openai_api_key: "sk-key1,sk-key2,sk-key3" # Comma-separated, automatically split and polled
```

### Method 2: Configure via environment variables

```bash
# Linux/macOS
export OPENAI_API_KEY="sk-key1,sk-key2,sk-key3"

# Haijun
export JUGLOW_API_KEY="sk-key1,sk-key2,sk-key3"
```

**Notes:**

- A single Key configuration behaves exactly the same as before, with no modification required
- With multiple Keys, each `chat()` call automatically rotates to the next Key
- The polling order is a sequential loop (Round-Robin), ensuring each Key is used evenly
- `juglow_api_key` also supports the above formats

## Q17: How do I orchestrate multiple Agents with pipeline_runner?

**A17:** `pipeline_runner` is a built-in multi-Agent orchestration engine: you declare an orchestration file (containing `agents` definitions and an optional `flow` order), and it builds a DAG according to `flow`, uses long-lived `hjb` Agents to schedule each stage in parallel, waits synchronously for completion, and passes the artifacts of the previous stage to the next stage.

**Minimal usage:**

```text
pipeline_runner(
  orchestration_file="builtin/agent_orchestration/simple_demo.yaml",
  working_dir="/path/to/workdir",
  max_workers=4
)
```

**Preview without executing first** (validate the orchestration file, view the DAG, do not create Agents):

```text
pipeline_runner(
  orchestration_file="builtin/agent_orchestration/simple_demo.yaml",
  working_dir="/path/to/workdir",
  dry_run=true
)
```

**Supported orchestration capabilities:**

- Dependencies and parallelism: `depends_on` (default = the previous stage, linear), `max_workers` (default 4).
- Conditions: `when` (restricted expression, whitelist evaluation, supports `stage.field` comparison and `&&`/`||`/`!`).
- Failure policy and retry: `on_error` (`abort`/`continue`/`skip_dependents`), `retry`.
- Gate: a stage with `gate: true` stops after completion, defaults to `approve=false`, and requires manual approval to proceed.
- Runtime loop: `loop(name, body, until, max_iterations)`, where `until` supports `file(path)` and `contains(text, substr)`.

**Orchestration file suffixes:**

- `.yaml` / `.yml`: organization orchestration (declares a set of Agents, may include `flow` to run as a pipeline).
- `.flow`: flow orchestration (declares the DAG structure with a Python DSL, suitable for dynamically generating stages).

For a detailed tutorial, see [Multi-Agent Orchestration: Driving Pipelines with pipeline_runner](../user-manual/00_getting-started/Multi-Agent_Orchestration_Driving_Pipelines_with_pipeline_runner.md).

## Q18: How do I approve the gate of an orchestration pipeline?

**A18:** When a stage declares `gate: true`, the pipeline will **stop** after that stage completes; by default `approve=false`, and manual confirmation is required to continue.

**Approving in the Web interface:** Open "Orchestration View"; when the gate stops, an approval overlay pops up, offering three actions:

- **Approve**: approve and continue to subsequent stages.
- **Reject**: reject; the pipeline does not continue.
- **Retry**: re-execute (can be used to make the stage run again).

When approving, you can fill in a note; the approval record (action / approver / note / stage / time) will be written to the log and displayed in the overlay.

**Re-running after approval:** Approving or retrying will trigger pipeline execution again with `approve=true`.

## Q19: How do multiple Agents send messages to each other to collaborate?

**A19:** Use the built-in tool `gateway_manager`, which supports three collaboration forms: group, chat room, and private chat (forwarded at the underlying level via the Web Gateway):

**Group (broadcast):**

```text
gateway_manager(action="create_group", group_name="refactoring group")
gateway_manager(action="join_group", group_id="<group_id>")
gateway_manager(action="send_group_message", group_id="<group_id>", message="planner done, artifact .df/plan.md")
```

**Chat room (Agents and humans in the same room):**

```text
gateway_manager(action="chat_list_rooms")
gateway_manager(action="chat_send_room_message", room_id="<room_id>", message="waiting for approval")
```

**Private chat (point-to-point):**

```text
gateway_manager(action="chat_send_private_message", receiver_id="<client_id or user_id>", message="send me the pass_rate")
```

Chat room / private chat messages are automatically prefixed with `[Agent name]`.

**Assigning work point-to-point and waiting for the result:**

```text
gateway_manager(action="send_to_agent", agent_id="<agent_id>", message="count the number of tests", wait=true, status_file="/tmp/agent_done.json")
```

When `wait=true`, it polls `status_file` (the Agent writes `{"status": "completed"|"failed"}` upon completion) to determine completion; it is recommended to pass `status_file` explicitly, which is more reliable than the fallback polling of `/status`.

**Note:** Group / chat room operations require the Agent to already have an `agent_id` (assigned by the gateway AgentManager); if not connected to the gateway, it will report `agent_id is not available`.

For details, see [Collaboration Mode Best Practices](../user-manual/00_getting-started/Best_Practices_for_Collaboration_Modes.md).

## Q20: How do I write the when conditional expression in an orchestration file?

**A20:** `when` is a **restricted expression** (whitelist evaluation, does not eval arbitrary code), used for "skip the stage if the condition is not satisfied". Supports:

- Referencing an upstream stage field: `stage.field` (taken from the upstream `status_file` and the artifact JSON content).
- Comparison: `==` `!=` `>=` `<=` `>` `<`.
- Logic: `&&` `||` `!`.
- Literals: numbers / strings / booleans.

**Example:**

```yaml
- stage: "notify"
  agent: "notifier"
  depends_on: ["validator"]
  when: "validator.pass_rate >= 0.9"
```

`loop`'s `until` condition additionally supports two whitelist functions on top of this:

- `file("relative artifact path")`: reads the body of an artifact file within work_dir (limited to within work_dir, ≤1MB, returns an empty string if it does not exist).
- `contains(text, substr)`: whether `text` contains `substr` (case-sensitive).

```yaml
until: "contains(file(\".df/report.json\"), \"\\\"pass_rate\\\": 1.0\")"
```

Fields are taken from the structured result of the upstream stage's `status_file` and the artifact JSON content; referencing a non-existent field yields `None`, and the comparison result is treated as `false`.

---
