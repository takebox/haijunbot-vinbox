# 5. Function Extension

The power of HaijunBot lies in its high extensibility. By creating your own tools and platforms, you can let HaijunBot interact with your private APIs, internal databases, proprietary systems, or any service you need.

This chapter will guide you through the entire process of creating, testing, and deploying custom features. HaijunBot supports three main ways to extend functionality:

1. **Standard tool development**: Define new tools by creating Python classes that follow the specification.
2. **MCP tool integration**: Connect to an external "Model Context Protocol" via configuration files to quickly integrate existing tool sets written in any language.
3. **Platform extension**: Integrate new large language model platforms by creating Python classes.

---

## 5.1 Standard Tool Development (Python Classes)

This is the most common and most direct way to develop tools.

### Tool Loading Locations

When HaijunBot starts, it automatically scans and loads tool files (`.py`) from the following locations:

1. **Built-in tools**: `src/haijunbot/haijunbot_tools/` (inside the HaijunBot source code)
2. **User-defined tools**: `~/.haijunbot/tools/` (the recommended place to store your personal tools)
3. **Additional tool directories**: A list of directories specified by the `tool_load_dirs` configuration.

#### Sharing and Syncing Tools via Git

Similar to methodologies, the design of `tool_load_dirs` also takes team collaboration and version control into account. You can use one or more Git repositories containing HaijunBot tools as shared tool libraries.

1. **Create a tool repository**: Create a Git repository to store the tools (`.py` files) shared by the team.
2. **Clone the repository**: Team members clone this repository locally.
3. **Set the configuration**: Set `tool_load_dirs` to point to the local path of that repository. You can specify multiple paths using list format.

```bash
# For example, clone the team's tool repository to ~/git/team-tools
git clone https://github.com/your-org/team-tools.git ~/git/team-tools

# Set in ~/.haijunbot/config.yaml
tool_load_dirs:
  - ~/git/team-tools
```

Once configured, HaijunBot will not only load tools from that directory, but also **automatically run `git pull` daily** to fetch the latest tool code, ensuring that team members' tool sets stay in sync.

#### Central Tool Repository

HaijunBot supports a central tool repository feature, which allows a team to set up a centrally managed tool repository so that all members can share and use a unified tool set.

##### Configuring the Central Tool Repository

Specify the Git repository URL of the central tool repository by setting the `central_tool_repo` configuration:

```yaml
# Set in ~/.haijunbot/config.yaml
central_tool_repo: "https://github.com/your-org/central-tools.git"
```

Once configured, HaijunBot will:

1. Automatically clone the central tool repository to `~/.haijunbot/central_tool_repo`
2. Automatically update the central tool repository daily (run `git pull`)
3. Load all tools from the central tool repository

##### Tool Loading Priority

When tools with the same name exist, the loading priority from low to high is:

1. Built-in tools (lowest priority)
2. Local tools (`~/.haijunbot/tools/`)
3. External directory tools (`tool_load_dirs`)
4. Central tool repository (highest priority)

If tools with the same name are found, the system displays a warning, and tools loaded later override those loaded earlier.

##### Sharing Tools to the Central Repository

You can share excellent tools you develop locally to the central tool repository for other team members to use:

```bash
# Share local tools to the central tool repository
haijunbot --share-tool
```

After running this command:

1. Displays the list of shareable tools in the local `~/.haijunbot/tools/` directory (excluding those that already exist)
2. Supports selecting a single tool or multiple tools (format: 1,2,3 or 4-9 or all)
3. **Note**: The tool files will be **moved** to the central repository rather than copied; the original files will be deleted
4. Automatically commit and push to the central tool repository

##### Usage Example

```bash
# 1. Configure the central tool repository (set in ~/.haijunbot/config.yaml)
# central_tool_repo: "https://github.com/team/haijunbot-tools.git"

# 2. Start HaijunBot (the central tool repository will be loaded automatically)
haijunbot

# 3. Develop a new tool and test it
echo 'class my_awesome_tool: ...' > ~/.haijunbot/tools/my_awesome_tool.py

# 4. Share to the central repository
haijunbot --share-tool
# Select my_awesome_tool and confirm
# The tool will be moved to the central repository, and team members will automatically get this tool the next time they start
```

### Core Specification for Tool Classes

A standard tool class must follow the specification below:

1. **File name must match tool name (critical)**: The tool file name (without the `.py` suffix) **must** be exactly the same as the `name` attribute inside the tool class. This is the hard requirement that allows HaijunBot to find and register the tool.
   - **Correct**: file `my_tool.py` -> class attribute `name = "my_tool"`
   - **Wrong**: file `my_tool.py` -> class attribute `name = "MyTool"` or `name = "some_other_name"`

2. **Class attributes**:
   - `name`: (string) The unique name of the tool, matching the file name.
   - `description`: (string) A clear description of the tool's function. The AI uses this description to decide when to use the tool.
   - `parameters`: (dictionary) The JSON Schema defining the parameters required by the tool.

3. **Class methods**:
   - `execute(self, args)`: (method) The actual execution logic of the tool.
   - `check()`: (optional `@staticmethod`) A static method used to perform a pre-check before loading the tool. If the `check()` method exists and returns `False`, the tool will be skipped and not loaded. This can be used to check whether dependencies exist, whether API keys are configured, and so on.

### Development Steps

Let's create a new tool that can read `.ini` configuration files.

#### Step 1: Create the tool file

According to the naming convention, we want to create a tool named `read_ini_section`, so the file name must be `read_ini_section.py`.

Create the `read_ini_section.py` file in the `~/.haijunbot/tools/` directory.

#### Step 2: Write the tool class

In the `read_ini_section.py` file, write the following code:

```python
import configparser
from typing import Dict, Any

class ReadIniSectionTool:
    # 1. Tool name (must match the file name "read_ini_section")
    name = "read_ini_section"

    # 2. Tool description (for the AI to read, must be clear)
    description = "Read all contents of the specified section in a .ini format configuration file."

    # 3. Parameter definition (using JSON Schema)
    parameters = {
        "type": "object",
        "properties": {
            "file_path": {
                "type": "string",
                "description": "The full path of the .ini file to read."
            },
            "section_name": {
                "type": "string",
                "description": "The name of the section containing the configuration items to read."
            }
        },
        "required": ["file_path", "section_name"]
    }

    # 4. (Optional) Pre-check
    @staticmethod
    def check() -> bool:
        # The dependency 'configparser' here is a standard library, so we directly return True.
        # If your tool depends on third-party libraries, you can check here.
        # try:
        #     import some_dependency
        # except ImportError:
        #     print("Warning: 'some_dependency' is not installed, the 'read_ini_section' tool is disabled.")
        #     return False
        return True

    # 5. Execution logic
    def execute(self, args: Dict[str, Any]) -> Dict[str, Any]:
        file_path = args.get("file_path")
        section_name = args.get("section_name")

        try:
            if not file_path or not section_name:
                raise ValueError("Error: both file_path and section_name must be provided.")

            config = configparser.ConfigParser()
            if not config.read(file_path):
                raise FileNotFoundError(f"Error: configuration file '{file_path}' does not exist or cannot be read.")

            if not config.has_section(section_name):
                raise ValueError(f"Error: no section named '{section_name}' was found in the configuration file.")

            section_content = dict(config.items(section_name))
            return {
                "success": True,
                "stdout": str(section_content),
                "stderr": ""
            }
        except Exception as e:
            return {
                "success": False,
                "stdout": "",
                "stderr": f"An error occurred while executing the tool: {str(e)}"
            }
```

#### Step 3: Test the tool

No additional registration is required; just restart `haijunbot` (`hjb`) and the new tool will be loaded automatically.

1. **Check loading**: Enter `'ToolUsage'` to view the tool list and confirm that `read_ini_section` is included.
2. **Natural language test**: Give HaijunBot a task, for example: `Please help me read the contents of the [database] section in the /path/to/my/app.ini file.`

## 5.2 MCP Tool Integration

MCP (Model Context Protocol) is a powerful mechanism that allows HaijunBot to communicate with external tool sets via standard input/output (stdio) or HTTP, among other methods. This means you can write tools in any language (such as Go, Rust, Node.js) and integrate them into HaijunBot as a whole.

### Configuration Method

MCP tools are configured through the `mcp` list in the `config.yaml` file. Each list item defines an MCP client.

HaijunBot supports the following three types of MCP clients:

#### 1. `stdio` (Standard Input/Output)

Used to integrate command-line programs that run locally and communicate via standard input/output.

- **Workflow**: When HaijunBot starts, it executes the `command` you specify, then sends JSON-RPC requests through `stdin` and receives responses through `stdout`.
- **Use cases**: Quickly wrap existing, standalone command-line tools into a tool set usable by HaijunBot.

**Configuration parameters**:

- `type`: `"stdio"` (required)
- `name`: The unique name given to this tool set (optional)
- `command`: The full command to start the tool program (required)
- `args`: List of command arguments (optional, array format)
- `env`: Environment variables (optional, object format)
- `enable`: Whether to enable this configuration (optional, defaults to `true`)

**Example**:

```yaml
mcp:
  - type: "stdio"
    name: "my_cli_tools"
    command: "/path/to/your/tool_program"
    args: ["--json-rpc", "--verbose"]
    env:
      CUSTOM_VAR: "value"
    enable: true
```

#### 2. `sse` (Server-Sent Events)

Used to connect to a remote HTTP server that supports Server-Sent Events. SSE allows the server to push an event stream to the client.

- **Workflow**: HaijunBot opens a persistent HTTP connection to `base_url` and receives the event stream from the server through this connection.
- **Use cases**: Scenarios that require real-time, long-lived connection communication with a remote service.

**Configuration parameters**:

- `type`: `"sse"` (required)
- `name`: Unique name (optional)
- `base_url`: Base URL of the remote MCP server (required)
- `auth_token`: Token used for authentication (optional)
- `headers`: Additional HTTP request headers (optional, object format)
- `enable`: Whether to enable (optional, defaults to `true`)

**Example**:

```yaml
mcp:
  - type: "sse"
    name: "realtime_data_service"
    base_url: "https://api.example.com/mcp"
    auth_token: "your-secret-token"
    headers:
      X-Custom-Header: "value"
    enable: true
```

#### 3. `streamable` (Streaming HTTP)

Used to connect to a remote server that supports standard streaming HTTP responses.

- **Workflow**: HaijunBot sends a standard HTTP POST request, and the server returns the response body as a stream. This is simpler than SSE, but it only streams in one direction (server to client).
- **Use cases**: Calling remote APIs that return large amounts of data and are suitable for chunked reading.

**Configuration parameters**:

- `type`: `"streamable"` (required)
- `name`: Unique name (optional)
- `base_url`: Base URL of the remote MCP server (required)
- `auth_token`: Token used for authentication (optional)
- `headers`: Additional HTTP request headers (optional, object format)
- `endpoint_path`: MCP server endpoint path (optional, defaults to `"mcp"`). If `base_url` already contains the endpoint path, this can be set to an empty string
- `timeout`: Request timeout array `[connect timeout, read timeout]` (optional, defaults to `[10, 300]`, unit: seconds)
- `enable`: Whether to enable (optional, defaults to `true`)

**Example**:

```yaml
mcp:
  - type: "streamable"
    name: "large_file_processor"
    base_url: "https://stream.example.com/api"
    auth_token: "your-secret-token"
    endpoint_path: "mcp" # optional, defaults to "mcp"
    timeout: [10, 300] # optional, [connect timeout, read timeout] in seconds
    enable: true
```

## 5.3 Platform Extension (Python Classes)

In addition to tools and MCP, HaijunBot also allows you to integrate new large language model platforms. This lets you connect to proprietary models, internally deployed LLM services, or any API that is not officially supported.

### Platform Loading Locations

HaijunBot automatically loads platform adapters (`.py`) from the following locations:

1. **Built-in platforms**: `src/haijunbot/haijunbot_platform/` (inside the HaijunBot source code)
2. **User-defined platforms**: `~/.haijunbot/models/` (the recommended place to store your personal platform adapters; the directory and `__init__.py` are created automatically on first run)

Note:

- The loading order is "user directory -> built-in directory". If a platform with the same name exists, the implementation loaded later overrides the one loaded earlier (in the current implementation this means "built-in overrides user-defined").

### Core Specification for Platform Classes

A standard platform class must follow the specification below:

1. **Inherit the base class**: Must inherit from `haijunbot.haijunbot_platform.base.BasePlatform`.
2. **Implement abstract methods**: Must implement all abstract methods in the base class. `PlatformRegistry` performs strict checks during loading.

According to the `REQUIRED_METHODS` in `src/haijunbot/haijunbot_platform/registry.py` and the definitions in `base.py`, a platform class must implement the following methods:

- `chat(self, message: str) -> Generator[str, None, None]`: The core conversation method, returning the model's response as a streaming generator.
- `name(self) -> str`: Returns the name of the current platform.
- `platform_name(cls) -> str` (class method): Returns the unique identifier of the platform, used to specify the platform in the configuration.
- `set_model_name(self, model_name: str)`: Sets the specific model name used for the current conversation.
- `get_model_list(self) -> List[Tuple[str, str]]`: Returns the list of models supported by the platform, in the format `(model ID, model description)`.
- `delete_chat(self) -> bool`: Clears the current conversation context.
- `set_system_prompt(self, message: str)`: Sets the system-level prompt.
- `upload_files(self, file_list: List[str]) -> bool`: (if supported) Implements the file upload logic.
- `support_upload_files(self) -> bool`: Returns whether the platform supports file uploads.
- `save(self, file_path: str) -> bool`: (optional) Saves the conversation state.
- `restore(self, file_path: str) -> bool`: (optional) Restores the conversation state.

### Development Steps

Suppose we want to integrate a new platform named `MyLLM`.

#### Step 1: Create the platform file

Create the `my_llm.py` file in the `~/.haijunbot/models/` directory.

#### Step 2: Write the platform class

In the `my_llm.py` file, write the following code skeleton:

```python
import os
from typing import Generator, List, Tuple
from haijunbot.haijunbot_platform.base import BasePlatform

class MyLLMPlatform(BasePlatform):

    def __init__(self):
        super().__init__()
        # Initialize the API client, session, etc. here
        self.api_key = os.getenv("MYLLM_API_KEY")
        if not self.api_key:
            raise ValueError("Environment variable MYLLM_API_KEY is not set")
        self._current_model = "default-model"
        self._conversation_history = []

    @classmethod
    def platform_name(cls) -> str:
        # This name will be used for platform in config.yaml
        return "my_llm"

    def name(self) -> str:
        return f"MyLLMPlatform ({self._current_model})"

    def set_model_name(self, model_name: str):
        self._current_model = model_name

    def get_model_list(self) -> List[Tuple[str, str]]:
        # Return the list of models supported by your platform
        return [("default-model", "Default Model"), ("pro-model", "Professional Model")]

    def chat(self, message: str) -> Generator[str, None, None]:
        # Implement the interaction logic with your LLM API here
        # ... call the API ...
        # Assume the API returns a complete string
        # for char in api_response:
        #     yield char
        self._conversation_history.append({"role": "user", "content": message})

        # Simulate a streaming response
        response_text = f"Simulated reply {message}"
        self._conversation_history.append({"role": "assistant", "content": response_text})
        yield response_text

    def set_system_prompt(self, message: str):
        # Implement the logic for setting the system prompt
        self._conversation_history.insert(0, {"role": "system", "content": message})

    def delete_chat(self) -> bool:
        # Clear the conversation history
        self._conversation_history = []
        return True

    def upload_files(self, file_list: List[str]) -> bool:
        # If not supported, directly return False
        print("The MyLLM platform does not support file uploads.")
        return False

    def support_upload_files(self) -> bool:
        return False

    def save(self, file_path: str) -> bool:
        # Optional implementation
        return False

    def restore(self, file_path: str) -> bool:
        # Optional implementation
        return False
```

#### Step 3: Configure and use

1. **Set the configuration**:

```yaml
# Set in ~/.haijunbot/config.yaml
platform: my_llm
model: pro-model # optional, depends on your implementation
ENV:
  MYLLM_API_KEY: "YOUR_API_KEY"
```

1. **Start HaijunBot**: Restart `haijunbot` and it will automatically load and use your new platform.

## 5.4 Methodology Sharing Configuration

HaijunBot supports team-level methodology sharing. By configuring a central methodology repository, team members can:

- Share and reuse proven solutions
- Automatically sync the latest methodology updates
- Avoid duplicated work and improve team efficiency

### Configuring the Central Methodology Repository

Add the following configuration in `~/.haijunbot/config.yaml`:

```yaml
# Central methodology Git repository URL
central_methodology_repo: https://github.com/your-org/haijunbot-methodologies.git

# Additional methodology loading directories (optional)
methodology_dirs:
  - ~/git/team-methodologies
  - /shared/methodologies
```

### How It Works

1. **Automatic cloning and updating**:
   - On first use, HaijunBot automatically clones the central repository to `~/.haijunbot/central_methodology_repo`
   - Automatically runs `git pull` on daily startup to update the latest methodologies

2. **Methodology loading sources**:
   - Project-level methodology directory (if present, highest priority)
   - Global methodology directory: `~/.haijunbot/methodologies`
   - Additional configured directories: directories specified by `methodology_dirs`
   - Central methodology repository: `~/.haijunbot/central_methodology_repo` (if `central_methodology_repo` is configured)

3. **Duplicate detection**:
   - When methodologies with the same name exist, the finally loaded version takes precedence
   - The sharing feature automatically detects and excludes methodologies that already exist

### Sharing Methodologies to the Central Repository

Use the following command to share local methodologies with the team:

```bash
haijunbot --share-methodology
```

Sharing process:

1. Automatically update the central repository to the latest version
2. Detect and display shareable methodologies (excluding duplicates)
3. Support batch selection of methodologies to share
4. Automatically copy files and commit them to the remote repository

### Best Practices

- **Consistent naming**: Use clear, descriptive names for problem types
- **Regular updates**: Periodically pull updates from the central repository
- **Quality control**: Ensure methodologies are fully verified before sharing
- **Documentation**: Include usage instructions and notes in the methodology

## 5.5 Rule System Extension

HaijunBot's rule system allows you to create and manage custom rules to guide the AI's behavior and code generation. Rules can be organized and shared in various ways, supporting team collaboration and knowledge reuse.

### Rule Types

HaijunBot's rules are organized as Markdown files (`.md`). Each file is a rule, and the file name (which may include a subdirectory relative path) is the rule name:

- Global rules: `~/.haijunbot/rules/<rule name>.md` (for example `~/.haijunbot/rules/rule.md`)
- Project rules: `.haijunbot/rules/<rule name>.md` (for example `.haijunbot/rules/rule.md`)

A rule file can use YAML Front Matter at the beginning to declare metadata (such as `description`). HaijunBot parses this header to generate the rule index and for automatic selection; the content after the Front Matter is the rule body. For example:

```markdown
---
description: Python code style specification
---

- Python code must follow the PEP 8 specification
- All functions must include type annotations and docstrings
```

> Note: HaijunBot does **not** support formats like `rules.yaml` in which "a single YAML file defines multiple named rules". Rules always exist as `.md` files in a directory.

### Rule Loading Locations and Priority

HaijunBot loads rules from the following locations by priority (from high to low):

1. **Central rule repository** (highest priority)
   - Configuration item: `central_rules_repo`
   - Storage location: `~/.haijunbot/central_rules_repo` (if the repository contains a `rules/` subdirectory, that subdirectory is used)
   - Supports automatic cloning and daily updates

2. **Project rule directory**
   - Location: `.haijunbot/rules/` directory
   - One rule per file; the file name (including subdirectory relative path) is the rule name

3. **Global rule directory**
   - Location: `~/.haijunbot/rules/` directory

4. **Configured rule directories**
   - Configuration item: `rules_load_dirs` (list format)
   - Supports multiple directories, loaded in configuration order

5. **Built-in rules** (lowest priority)
   - Rules built into the HaijunBot system (`builtin/rules/`), used as a fallback

### Configuring the Central Rule Repository

Add the following configuration in `~/.haijunbot/config.yaml`:

```yaml
# Central rule repository Git URL
central_rules_repo: https://github.com/your-org/haijunbot-rules.git

# Additional rule loading directories (optional, list format)
rules_load_dirs:
  - ~/git/team-rules
  - /shared/rules
```

Once configured, HaijunBot will:

1. Automatically clone the central rule repository to `~/.haijunbot/central_rules_repo`
2. Automatically update the central rule repository daily (run `git pull`)
3. Load all rules from the central rule repository

### Creating Rules

#### Method 1: Create standalone rule files

Create a rule file in the project `.haijunbot/rules/` directory or the global `~/.haijunbot/rules/` directory:

```bash
# Create project rules
mkdir -p .haijunbot/rules
echo "# TDD rules
- All new features must have tests written first
- Tests must cover the main feature paths and boundary cases
- The todo!() macro is forbidden" > .haijunbot/rules/tdd

# Create global rules
mkdir -p ~/.haijunbot/rules
echo "# Code style rules
- Python code must follow the PEP 8 specification
- All functions must include type annotations and docstrings" > ~/.haijunbot/rules/python_style
```

#### Method 2: Organize with subdirectories and describe with YAML Front Matter

The rule directory supports recursive traversal of subdirectories, so you can use subdirectories to categorize rules; the rule name is its relative path. For example:

```bash
mkdir -p .haijunbot/rules/deployment
cat > .haijunbot/rules/deployment/version_release.md <<'EOF'
---
description: Version release process specification
---
- All tests must pass before release
- Version numbers follow the semantic versioning specification
EOF
```

At this point the name of this rule is `deployment/version_release.md` (in project rules it can be written as `project:deployment/version_release.md`).

The `description` in the Front Matter is written to the rule index for the AI to reference when automatically selecting rules; the body content is the actual rule text injected into the AI.

### Using Rules

#### Using rules in CodeAgent

```bash
# Use multiple rules (comma-separated)
hca --rule-names tdd,clean_code -r "Implement the user login feature"

# Use project-specific rules
hca --rule-names project_style -r "Add a new API endpoint"
```

#### Dynamically inject rules in interactive input

Use the `'<rule:rule_name>'` marker in user input to dynamically inject rules:

```bash
hca
# Then enter: '<rule:tdd>' implement the user login feature
```

The system will automatically find and inject the corresponding rule content.

### Sharing Rules to the Central Repository

You can share excellent rules you develop locally to the central rule repository for other team members to use. The rule sharing feature is implemented through `RuleShareManager` and a CLI command is already provided:

```bash
# Share local rules to the central rule repository
haijunbot --share-rule
```

**Note**: Shareable rule sources include the project rule directory (`.haijunbot/rules/`), rule directories configured by `rules_load_dirs`, and the built-in rule directory (`builtin/rules/`); rules in the central rule repository itself are excluded.

Rule sharing process:

1. Update the central repository to the latest version
2. Detect and display the list of shareable rules (excluding those already existing in the central repository)
3. Support selecting a single rule or multiple rules (format: `1,2,3` or `4-9` or `all`)
4. **Note**: The rule files will be **copied** to the central repository (the original files are kept)
5. Automatically commit and push to the central rule repository

### Rule Loading Priority Example

Suppose you have the following rule configuration:

```text
Central rule repository: tdd, clean_code
Project .haijunbot/rules/: tdd, project_style
Global ~/.haijunbot/rules/: python_style, clean_code
Configured rule directories (rules_load_dirs): security
```

When using `--rule-names tdd,clean_code`:

- `tdd` rule: loaded from the central rule repository (highest priority)
- `clean_code` rule: loaded from the central rule repository (if present), otherwise loaded from the global `~/.haijunbot/rules/`

### Rule Best Practices

1. **Naming conventions**: Use clear, descriptive rule names separated by underscores (such as `python_style`, `tdd_rules`)

2. **Content organization**:
   - Keep rules concise and clear, using bullet lists
   - Each rule focuses on one topic (code style, testing, security, etc.)
   - Avoid lengthy background descriptions

3. **Priority management**:
   - Put general rules in the global rule directory
   - Put project-specific rules in the project rule directory
   - Put team-shared rules in the central rule repository

4. **Version control**:
   - Project rules should be committed to the Git repository
   - The central rule repository uses Git for version management
   - Regularly update the central rule repository to get the latest rules

5. **Rule reuse**:
   - Reference general rules in multiple rules
   - Use subdirectories to categorize rules and use YAML Front Matter for supplementary descriptions to facilitate management and maintenance
   - Regularly review and update rule content

## 5.6 Best Practices

- **Naming convention is key**: Be sure to follow the rule that the **file name must match the `name` attribute**; this is the most common cause of tool loading failures.
- **Stay atomic**: Each tool should do one thing and do it well. Complex logic should be split into multiple tools.
- **Describe clearly**: The `description` is written for the AI and is the most critical factor in determining whether the tool can be used correctly.
- **Robust error handling**: The `execute` method must be able to handle errors properly and return meaningful error messages through `stderr`.
- **Precise parameter definition**: Define `parameters` as precisely as possible. Use the `description` field to explain each parameter in detail.
- **Return values are strings**: The `stdout` and `stderr` fields should be strings. If the result is a complex data structure, serialize it into a string (such as `json.dumps()`).

### Development Workflow

1. **Create a feature branch**:

   ```bash
   git checkout -b feature/my-new-tool
   ```

2. **Develop and test**:
   - Create your code files in the appropriate directory
   - Write unit tests (if applicable)
   - Test your feature locally

3. **Code style**:
   - Use Python 3.12 features (the project requires `requires-python = "==3.12.*"`)
   - Follow the PEP 8 code style guide
   - Use type annotations to improve code readability

4. **Commit conventions**:
   Use the semantic commit message format:

   ```bash
   git commit -m "feat(tools): add a database query tool"
   git commit -m "fix(platform): fix the streaming response issue of the OpenAI platform"
   git commit -m "docs: update the tool development guide"
   ```

## 5.8 Contributing Code

We welcome contributions from the community! If you have developed useful tools or platform adapters, you can contribute them to the HaijunBot project in the following ways:

### Contribution Process

1. **Fork the project**:
   Fork the HaijunBot main repository to your account on GitHub.

2. **Create a feature branch**:

   ```bash
   git checkout -b feature/AmazingFeature
   ```

3. **Commit your changes**:

   ```bash
   git commit -m 'feat(scope): Add some AmazingFeature'
   ```

4. **Push the branch**:

   ```bash
   git push origin feature/AmazingFeature
   ```

5. **Create a Pull Request**:
   Create a Pull Request on GitHub and describe your changes in detail.

### Contribution Guidelines

- **Code quality**: Ensure the code is thoroughly tested with no obvious bugs
- **Complete documentation**: Add the necessary documentation for new features
- **Backward compatibility**: Try to maintain backward compatibility of the API
- **Commit messages**: Use clear, standardized commit messages
- **Single responsibility**: Each PR should address only one issue or add one feature

### Code Review

After submitting a PR, maintainers will review the code. Please be patient and respond actively to review comments. Common review points include:

- Whether the code style conforms to the project specification
- Whether there is sufficient error handling
- Whether there are potential performance issues
- Whether the documentation is complete and clear
