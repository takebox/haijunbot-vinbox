# Strengths and Weaknesses Analysis

## Research Goals

Comprehensively analyze an open-source project's technical highlights and strengths, its existing limitations and shortcomings, and its applicable scenarios and constraints, providing an objective basis for technology selection.

## Research Steps You Must Perform

### Step 1: Identify Technical Highlights and Strengths

**Strength dimensions that must be analyzed:**

- **Performance strengths**: outstanding performance
- **Usability strengths**: user experience and learning curve
- **Maintainability strengths**: code quality, architecture design
- **Extensibility strengths**: extension mechanisms and plugin systems
- **Stability strengths**: reliability, fault tolerance
- **Ecosystem strengths**: community activity, third-party support

**Keywords to search:**

- "[project name] advantages"
- "[project name] why use"
- "[project name] benefits"
- "[project name] vs [competitor] advantages"

**Information sources:**

- The Why section of the official documentation
- Technical review articles
- User cases and feedback
- read_webpage to read comparison analysis

### Step 2: Analyze Limitations and Shortcomings

**Shortcoming dimensions that must be researched:**

- **Performance limitations**: performance bottlenecks and limits
- **Feature limitations**: missing functions or features
- **Complexity limitations**: complexity of use and deployment
- **Compatibility limitations**: compatibility with platforms and tech stacks
- **Maintainability shortcomings**: code quality, technical debt
- **Stability shortcomings**: known bugs and issues

**Keywords to search:**

- "[project name] limitations"
- "[project name] disadvantages"
- "[project name] known issues"
- "[project name] drawbacks"

**Information sources:**

- The Limitations section of the official documentation
- The issue tracking system
- Critical articles on technical blogs
- Negative user feedback

### Step 3: Analyze Applicable Scenarios

**Applicable scenarios that must be clarified:**

- The application scenarios the project is best suited for
- Best-practice use cases
- The applicable range of scale and load
- Tech stack and environment requirements

**Key research questions:**

- Under what circumstances this project should be chosen
- Under what circumstances this project should not be chosen
- Whether the project is best suited for server-side/client-side/embedded, etc.
- The project's typical deployment scenarios

**Keywords to search:**

- "[project name] use cases"
- "[project name] best practices"
- "[project name] when to use"
- "[project name] deployment scenarios"

**Information sources:**

- The Use Cases section of the official documentation
- User cases and success stories
- Practice articles on technical blogs
- Community discussions

### Step 4: Analyze Constraints

**Limits that must be researched:**

- Technical limits (language, platform, dependencies)
- Performance limits (concurrency, throughput, latency)
- Scale limits (data volume, number of users)
- Feature limits (unsupported functionality)
- License limits (commercial use requirements)

**Keywords to search:**

- "[project name] requirements"
- "[project name] limitations"
- "[project name] constraints"
- "[project name] system requirements"

**Information sources:**

- The Requirements section of the official documentation
- Installation and deployment documentation
- Performance benchmark reports
- License documentation

### Step 5: Collect User Feedback and Reviews

**Feedback that must be analyzed:**

- Positive user reviews and praise
- Negative user reviews and criticism
- Community discussions and controversies
- Third-party reviews and suggestions

**Keywords to search:**

- "[project name] review"
- "[project name] experience"
- "[project name] feedback"
- "[project name] Reddit/Hacker News"

**Information sources:**

- The GitHub Discuss community
- Technical forums (Reddit, Stack Overflow)
- Reviews on technical blogs
- Social media discussions

### Step 6: Compare the Evolution Across Versions

**Content that must be analyzed:**

- Improvements from old versions to new versions
- How historical issues were resolved
- Cleanup of technical debt
- New features and improvements

**Information sources:**

- The CHANGELOG file
- Version release notes
- Version comparison documents
- Issue and PR history

## Research Output Requirements

### Document Structure

**Document that must be produced:** `05_pros_cons.md`

**The document must contain the following sections:**

1. Technical highlights and strengths
2. Limitations and shortcomings
3. Applicable scenario analysis
4. Constraint description
5. User feedback summary
6. Version evolution analysis
7. Reference list

### Content Quality Requirements

- **Must**: be objective and fair, avoiding subjective bias
- **Must**: provide concrete examples and data support
- **Must**: distinguish strengths from applicable scenarios
- **Must**: all analysis has source citations
- **Forbidden**: listing only advantages while ignoring shortcomings
- **Forbidden**: subjective judgments based on guesses

## Research Depth Check

After completing this stage of research, you must confirm:

- [ ] You comprehensively understand the project's technical strengths
- [ ] You clearly recognize the project's limitations
- [ ] You clarify the project's applicable scenarios
- [ ] You understand the project's constraints
- [ ] You have collected sufficient user feedback
- [ ] All analysis has an objective basis

## Analysis Framework

### SWOT Analysis Framework

**Must include:**

- **Strengths**: the project's strong points
- **Weaknesses**: the project's weak points
- **Opportunities**: potential room for growth
- **Threats**: external challenges faced

### Scenario Applicability Analysis

**Must answer:**

- What scenarios is it suitable for? Why?
- What scenarios is it not suitable for? Why?
- Under what circumstances can this project be considered?
- Under what circumstances should another option be chosen?

### Strength Verification Framework

**Must include:**

- The concrete manifestation of the strengths
- The data support for the strengths
- The applicable range of the strengths
- The limitations of the strengths

## Common Mistakes

**❌ Wrong approaches:**

- Listing only advantages while ignoring shortcomings
- Lacking concrete examples, with only abstract descriptions
- Not distinguishing the applicable scenarios of the strengths
- Ignoring user feedback and actual usage experience

**✅ Correct approaches:**

- Be objective and comprehensive, listing both strengths and analyzing shortcomings
- Provide concrete data and case support
- Analyze the applicability of strengths in specific scenarios
- Fully consider user feedback and actual usage

## Practical Tips

**In-depth research strategy:**

1. Look at the project's known issues to understand common problems
2. Read users' questions and complaints on forums
3. Analyze the project's star growth trend on GitHub
4. Read competitor comparison articles to understand a third-party perspective
5. Read user experience sharing on technical blogs
6. Follow the project's roadmap to understand future improvement directions
