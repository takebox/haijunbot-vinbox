# Acceptance Scenario Isolation Discipline (Holdout Discipline)

## Core Principles

The dark factory's trust is built on **isolated evaluation**: the coding agent **never sees** the acceptance scenarios (holdout scenarios); an independent evaluator agent tests the produced code with these hidden scenarios.

This is train/test separation—preventing the reasoning model from "overfitting" to the specs it has seen. Research confirms that reasoning models cheat for the specs they can see, even with explicit counter-instructions.

## Discipline Requirements

1. **Scenario isolation**: holdout scenarios are generated by an independent stage and remain invisible to the coding agent throughout.
2. **Independent evaluator**: a dedicated validator agent holds the holdout scenarios and runs the tests, strictly separated from the generator.
3. **No leakage**: no stage may disclose the contents of the holdout scenarios to the coding agent.
4. **Multiple sampling**: run each scenario 3 times, with 2-of-3 passing to smooth out LLM variance.

## Generation Method

Use the `holdout_generator` tool to generate holdout scenarios. The generated scenarios are pure-English acceptance tests, marked as invisible to the coding side, and provided only to the evaluator.

## How It Is Implemented in the Pipeline

1. **Independent generation stage**: In the flow, set a `holdout` stage after the planner and before the generator, executed by an independent agent (`df_holdout`)—it reads the NLSpec, uses `holdout_generator` to generate scenario skeletons, then refines them into acceptance scenarios for this feature based on the spec's Goal/Interfaces, and writes `.df/holdout.json` to disk (marked `hidden=true`).
2. **Consistency**: each scenario must correspond to a Goal or Interface contract in the spec, ensuring the scenarios originate from the spec.
3. **Isolated transfer**: `.df/holdout.json` is **only used as the validator's `input` and is never injected into the generator** (the generator's `input` is only `.df/plan.md`).
4. **Independent evaluation**: the validator reads `.df/holdout.json` to execute the scenarios, records pass/fail per scenario, and produces `.df/report.json`.

## Gate Criteria

- **Scenario pass rate ≥90%**: only then is passing the gate recommended.
- **<90%**: considered substandard; proceed to retry or human approval.
- **False positive rate <5%, human override rate <10%**: only then consider relaxing to automatic merging.

## Common Pitfalls

- **Leaking scenarios (L4+)**: if the coding agent sees the holdout scenarios, it will optimize for them rather than solving the problem. **Strict isolation is non-negotiable**.
- **Premature automatic merging**: only enable the automatic gate after collecting 20-30 PRs demonstrating that the evaluator agrees with human judgment.
- **Too few scenarios**: an insufficient sample cannot assess true quality.

## Relationship to "Not Fully Unattended"

This plugin adopts a "not fully unattended" design: after the evaluator produces the pass/fail report, it **does not merge automatically**, but hands it to a human approval checkpoint. Humans review the pass/fail report and the details of failed scenarios, not the code line by line. This preserves the objectivity of isolated evaluation while controlling the trust boundary through human approval.
